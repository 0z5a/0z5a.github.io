1 Introduction

Looped, or recurrent-depth, language models reuse one block of transformer layers many times per token (Geiping et al., 2025; Zhu et al., 2025; McLeish et al., 2025). Because a shallow run of the same weights can serve as a draft, they support self-speculative decoding without a separate draft model by drafting with d≪R loops and verifying at full depth (Geiping et al., 2025; Cho et al., 2026; Ha & Kim, 2026; Li et al., 2026; Liu et al., 2026). Weight reuse keeps parameter storage small, but the KV cache grows with recurrent depth. Every loop of every recurrent layer writes its own keys and values, so Huginn-0125 stores 2,788 KB per token, against 169 KB if only one plane were kept. At the 808-token sequence length of the batch-6 and batch-8 memory cells, a 95 GB budget then holds 36 sequences with the full cache and 302 with one plane (Section 3.5).

Which planes have to be stored? Huginn’s own code offers caches that keep fewer planes (Geiping et al., 2025), Ouro reports that the last loop’s KV suffices for its model’s decoded tokens, though not for the prompt (Zhu et al., 2025), and WaveFront shows that cross-loop sharing raises self-speculative speed (Ha & Kim, 2026). Keeping only the deepest plane is the cheapest choice, and its errors invite an obvious repair: keep every plane for the W most recent positions, where decoding and speculative verification happen, and let older positions share the deepest plane (Figure 1). The window also makes batched verification consistent with sequential decoding. We call this policy RIPE (Recent-window Intact, deepest Plane Elsewhere), built it, and tested it on three looped models in ten pre-registered GPU batches, whose decision rules and predictions were frozen before each run, and in audited reruns on other hardware. Many predictions failed; the supplementary appendix lists all of them.

This paper is the resulting negative result. The window selects positions by recency, but on every model the cost of the deepest plane is set by how far the late loops’ planes have converged, which we call ripeness and which is a property of the model, and by which positions share, which for a prompt of a few hundred tokens is almost all of them. Small post hoc models (Table 1) make this quantitative on Huginn and Raven.

Contributions.

  • A three-part negative result. On Raven-Llama the deepest plane is already indistinguishable from bf16 rounding, so the window is unnecessary (Section 5.1). On Huginn-0125 a 64-position window removes most of a replay-error tail, but the RIPE decoder is slower, larger and not measurably closer to the full cache than the deepest plane alone, so the window is ineffective (Section 5.3). On pretrained Ouro-1.4B the prompt lies outside the window, and with W≤64 the model almost never finishes an answer that the full cache finishes, so the window is insufficient (Section 5.4).
  • Why: ripeness and position, not recency. A sensitivity model (KL grows as a power 1.82–2.70 of a prefix-KV perturbation, late loops far more sensitive) and a ripening model (approximately geometric convergence of planes with a bf16 floor) predict the deepest plane’s error to within a factor of two and separate Raven from Huginn (Sections 3.1, 3.2). Neither quantity depends on a position’s recency; the window changes how many positions share, not what sharing costs them.
  • Replay tails are not decoder quality. The teacher-forced replay tail that motivated the window falls by 89% on Huginn, while the decoder it motivated shows no detectable difference on 22 problems (ratio 0.80 [0.39, 1.25]). Per-head position filtering, attention sinks and a second plane do not help either (Section 5.6).
  • What the window does provide, and what it does not. When W≥γ, batched verification under RIPE computes the same values as sequential RIPE decoding in exact arithmetic (Section 4); deepest-plane drafts keep 88% of the deepest plane’s acceptance gain. These concern schedules and speed, not closeness to the full cache. In bf16, execution shape alone changes trajectories at rates comparable to the cache effects: cuDNN attention makes GH200 decoding non-reproducible, and Ouro’s sequential-versus-batched gate fails in bf16 on two GPUs but passes in fp32 (Sections 5.7, 5.4).
  • Performance models and audited evidence. Acceptance, cost, memory and throughput models, two checked on held-out data (Sections 3.3–3.5); frozen inputs and independent audits of every rerun.

2 Background

Looped models. A prelude P of npre layers embeds token xt; a core block B of ncore layers runs R times on a state initialized at random; a coda C of ncoda layers produces logits:

st(r)=B(st(r−1),P(xt);𝒞<t(r)),r=1,…,R,(1)

zt=C⁡(st(R)).(2)

At loop r, each core layer emits keys and values for token t; we call loop r’s keys and values over all core layers plane r, written (K(r),V(r)). In the full cache, the query of token t at loop r attends to plane r of every prefix position. Huginn-0125 (Geiping et al., 2025) has npre=ncoda=2, ncore=4, R=32, and 55 heads of width 96. Raven-Llama (McLeish et al., 2025) has npre=ncoda=4, ncore=6, R=32, and grouped-query attention with 8 KV heads of width 64.

Cache policies. A policy π⁡(r,t,j)∈{1,…,R} names the plane of prefix position j that token t reads at loop r (Figure 1). The full cache has π=r; the deepest-plane cache has π=R. Huginn’s compress-sS keeps S core slots and overwrites them modulo S; with S=ncore the last writer of every slot is loop R, so it is exactly the deepest-plane cache. Huginn’s slot map hard-codes npre=2; for Raven we use the general map slot=(step−npre)modS+npre, checked on CPU against direct substitution. With b=2⋅2​Hkv​dh bytes per layer per token in bf16 (K and V, two bytes each), an L-token sequence needs

Mfull​(L)=b​L​(npre+ncoda+R​ncore),(3)

Mdeep​(L)=b​L​(npre+ncoda+ncore),

that is, 2,788 vs. 169 KB per token on Huginn (6.1%) and 410 vs. 28.7 KB on Raven (7.0%).

Self-speculative decoding. A draft runs γ tokens through d loops each; one verification pass runs the block of γ+1 tokens through all R loops at once, accepts the longest prefix on which draft and verifier agree (greedy), and adds one token from the verifier. We write τ for tokens per verification.

Measurement modes. Teacher-forced prefill replaces attention with an explicit fp32 softmax, records each call’s keys and values, and substitutes any loop’s prefix K/V by another plane; the last 64 positions act as decoded tokens. Generation decodes greedily with the full cache, then replays each trajectory through the arm and through an fp32 full cache, which sets the precision floor. We report KL(reference∥arm) per position.

3 Models

All models in this section are post hoc: we built them after the pre-registered batches had run. We label each check by whether the data it uses entered the fit.

3.1 Sensitivity: deep loops are more sensitive to prefix KV

Let δr be the relative perturbation of the prefix keys and values that loop r reads. To first order the logits move by Δ​z≈∑rJr​δr. With p=softmax⁡(z) and p′=softmax⁡(z+Δ​z),

KL(p∥p′)=12Δz⊤F(p)Δz+O(∥Δz∥3),(4)

where F⁡(p)=diag⁡(p)−p​p⊤. Dropping cross terms, KL≈∑rsr​‖δr‖2 for small perturbations: quadratic, weighted by a per-loop sensitivity sr. We fit the exponent rather than fix it at 2.

The pre-registered test of batches 2 and 9 substitutes the prefix K/V of either loops 2–9 (shallow) or loops 25–32 (deep) by plane p∈{1,4,8,16,24,32}, measures the size ‖δ‖ as the root-sum-square of the relative distances over loops, layers, keys and values, and regresses log⁡KL at the first decoded position on region and log⁡‖δ‖ (Figure 2a,b). In fp32 the size exponent is 1.82 [1.68, 1.97] on Raven, consistent with the second-order term, and g=2.70 [2.52, 2.87] on Huginn, which excludes 2: Huginn’s shallow loops follow the quadratic (slope 2.06) but its deep loops are steeper (2.71). The largest substitutions (plane 1) are outside the small-perturbation regime of Eq. (4); Raven’s shallow region sits at the fp32 resolution. At equal size the deep region is e15.0 [e14.2, e15.8] (Huginn, 40 texts) and e12.8 [e12.0, e13.7] (Raven, 40 texts) times more sensitive. In bf16 the coefficients are 6.7 and 3.8; there 23% and 21% of the rows sit at the bf16 KL floor, which caps the measurable gap.

The consequence for caching: accuracy of the deep loops’ prefix K/V deserves priority. At equal storage, keeping the deepest plane agrees with the full cache at the first decoded position in 0.990 of texts, whereas a window of the first four loops, the starting plan’s choice, reaches 0.845 (batch 2; sharing every 8 or 4 loops gives 0.980 and 0.970).

3.2 Ripening: an approximate geometric trend

Let Δr=‖K(r)−K(R)‖/‖K(R)‖ over prefix positions, averaged over layers and texts, and likewise for values. Figure 2c shows that in fp32, Δr≈c​ρr from loop 8 on (on Raven the rate drifts upward with r; largest log residual 0.51). Huginn ripens at ρ=0.88 per loop (half-life 5.2 loops) and Raven at ρ=0.81 (3.3 loops); values behave the same way (ρ=0.87 and 0.81). In bf16 the curve flattens at a rounding floor,

Δrbf16≈(c​ρr)2+Δ∞2,(5)

and this one extra parameter reproduces the bf16 curve (Δ∞=0.0072 for Huginn’s keys, 0.0048 for Raven’s). Over the deep loops 25–31, Huginn’s keys are still 0.0116 away from plane R in bf16, above its floor, while Raven’s are at its floor (0.0047); in fp32 Raven’s are 61 times closer than Huginn’s.

Deepest-plane error. Storing only plane R sets δr=Δr for every r<R. With the sensitivity profile of Section 3.1, we approximate the total by the deep-loop contribution, neglecting other loops and cross terms. The fitted region model gives

KLdeep≈ea+b​Sg,S2=ncore​∑r=2531(ΔrK​ 2+ΔrV​ 2).(6)

For Huginn in fp32 this predicts 3.6×10−6 at the first decoded position from the ripening curve, or 1.7×10−6 from the measured perturbation size; the deepest-plane cache, which the fit did not use, measures 3.2×10−6 (median). The agreement is to within a factor of two, not better. Substituting plane R in the shallow loops alone costs only 2.4×10−9. For Raven the model predicts 1.8×10−8 (4.7×10−9 from the measured size), 202–366 times less than for Huginn, and the measurement is at the fp32 resolution (median below 10−9, mean 2.7×10−8).

Remark 1 (ripeness test, a hypothesis). If the deep loops’ Δr is at the bf16 floor, deepest-plane storage perturbs those loops about as much as rounding already does, and its cost should be indistinguishable from a precision change; otherwise it should exceed it. Both models fit this reading (Section 5.1), but two models cannot establish it. The test needs one prefill per prompt and no generation.

3.3 Acceptance

If each draft token is accepted with probability α, independently of its position in the block, the tokens per verification follow (Leviathan et al., 2022; Chen et al., 2023)

τ⁡(α,γ)=1−αγ+11−α.(7)

Batch 3 simulated greedy self-speculation on 60 GSM8K problems with γ=4 and recorded acceptance at each draft position given that all earlier ones were accepted. It is flat: across positions it varies by at most 0.06 (full cache) and 0.04 (deepest plane) for d∈{2,4,8} (Figure 5a), and Eq. (7) with the mean αd matches the simulated τ within 2.6%. Out of sample, the batch-3 values predict τ=3.40 (full) and 4.33 (deepest plane) at d=γ=4; batch 8’s real batched-verify decoder measured 3.34 and 4.47 on 24 other GSM8K problems and 3.61 and 4.53 on 12 more. Drafts that read the deepest plane accept α4=0.93 instead of 0.81, and their rejection rate falls faster with draft depth: 1−αd∝ρad with ρa=0.66 against 0.76.

3.4 Cost

We assume that at batch size 1 our eager decoder is bound by kernel launches and weight reads, so that a forward costs in proportion to the layer passes it runs, c⁡(d)=npre+d​ncore+ncoda, almost regardless of how many tokens it carries. A sequential token costs c⁡(R)=132 passes; a block costs γ​c​(d)+c⁡(R), scaled by one overhead factor η for everything else. The speed-up over sequential decoding is then

S⁡(d,γ)=τ⁡(αd,γ)​c​(R)η⁡(γ​c​(d)+c⁡(R)).(8)

With η=1 and the measured block counts, Eq. (8) gives 2.24× and 2.80× against measured 2.09× and 2.58× (12 problems, d=γ=4). One factor η=1.07, fitted to all 24 per-problem timings at once, gives 2.08× and 2.61×, with per-problem errors up to 5.4%. Sequential decoding is equally fast with either cache (ratio 1.00), so the gain of the deepest plane is entirely its higher acceptance. With η fixed at this value, Eq. (8) predicts the two RIPE decoders of Section 5.3, run later on another GH200 machine, at 2.06× and 2.59× over sequential RIPE; they measured 2.06× and 2.66×. Applied post hoc to the full-cache and deepest-plane decoders of the same run, it is off by −10% and +6%.

Figure 5b extrapolates Eq. (8) over γ (flat acceptance was tested only to γ=4, and only d=γ=4 was timed): deepest-plane drafts raise the speed-up and move the best block length from γ=5 (1.98×) past γ=8 (2.87×).

3.5 Memory and fixed-memory throughput

WaveFront’s batched emulator (Ha & Kim, 2026) allocates exactly Eq. (3): over all 26 cells of batches 6 and 8 (sequences of 808 tokens; 0, 1 or 4 shared core slots), the reported cache size matches the formula to its printed precision. Peak reserved memory adds o0+o1​B, with o0=7.2 GB and o1=0.18 GB (full) or 0.15 GB (one slot) per sequence, fitted on batch 6. This predicts the 9 batch-8 cells, which ran on another node and up to B=256, within 0.15%. Under the pre-registered 95 GB budget, the largest batch is Bmax=36 with the full cache (2.25 GB per sequence) and 302 with one slot.

Throughput per configuration follows T⁡(B)=B/(a+b​B) (largest residual 2% and 6%); the full cache saturates at T∞=449 tokens/s and one shared slot at 689 (batch 6). The fixed-memory advantage of sharing has two factors (Figure 5c): at the full cache’s best batch (B=32) the shared slot is already 1.67× faster, and memory then lets it run B=64, another 1.34×, for 2.24× in all (Section 5.5).

4 The policy under test: RIPE

RIPE (Recent-window Intact, deepest Plane Elsewhere) reads the deepest plane for old positions and the own plane for the W most recent ones:

πRIPE​(r,t,j)={r,t−j≤W,R,t−j>W,(9)

MRIPE​(L)=Mdeep​(L)+b​ncore​(R−1)​min⁡(W,L).(10)

The accounting assumes a deepest-plane array for all positions plus a ring buffer of W×(R−1) core planes, which the reported GPU experiments do not allocate; a position leaving the window drops its non-deepest planes. At L=1024, W=64 costs 341 MB on Huginn (11.9% of 2,855 MB) and 54 MB on Raven (12.8%), i.e. about 168 MB per Huginn sequence over the deepest-plane cache (Table 2). These are calculated values: the Huginn decoder emulates storage (Section 5.3), while the Ouro runs use a physical ring buffer (Section 5.4; CPU checks in the supplementary appendix).

Algorithm 1 describes a nonterminal step; stopping rules may truncate the emitted sequence. The correction or bonus token is processed at the next step. In the emulator, invalidation is logical: the next write position excludes the unused suffix from attention, and later passes overwrite it.

Proposition 1 (sequential self-consistency under RIPE). Consider a causal model whose operations use the same per-position initialization and do not couple a token to future positions. Let the committed prefix state be identical in both executions, stochastic layers be disabled, and the block pass retain every prefix plane needed by its queries until those queries finish. If W≥γ, verification of a fixed block of γ+1 tokens under πRIPE computes, in exact arithmetic, the same logits and cached keys and values as processing that block sequentially under the same policy.

Proof sketch. Use induction over recurrent loops and, within each loop, causal positions. The two schedules start from the same prefix and per-position state. For a block query at t, each earlier block position j has t−j≤γ≤W, so both schedules read its loop-r plane; it is available from the current loop in the block pass and from the cache in the sequential pass. A committed prefix position j<t0 read at loop r with t−j≤W also satisfies t0−j≤W, so its loop-r plane was retained at block entry. Otherwise both schedules read its stored plane R. By the induction hypothesis the inputs to each causal operation agree, so its output and emitted K/V agree. The coda then produces equal logits. In particular, the committed K/V for an accepted prefix agree. ∎

This compares execution schedules of the same approximate cache; it says nothing about their distance from full-cache decoding. In floating point, kernel shapes and reduction orders change logits, so it does not guarantee bitwise identity.

The deepest-plane cache (W=0) violates the premise: a block token cannot read plane R of an earlier block token, which does not exist yet, so batched verification reads plane r there, and outputs depend on where blocks start. Section 5.2 measures how much this matters on Huginn.

Drafts and the choice of W. Under the proposition’s assumptions, greedy verification preserves the sequential trajectory of the same RIPE target regardless of the draft tokens; this is not a full-cache equivalence claim. Reading plane R gives drafts the higher acceptance of Section 3.3. The block length sets W≥γ; we use W=64, the window that reduced Huginn’s replay tail (Section 5.1), as the tested operating point.

5 Evaluation

Protocol. In the experimental records, each batch had a pre-registration with decision rules and predictions, a frozen file table (SHA-256), on-node CPU self-tests, and an archive verified on both ends. Separate unscored Nsight Compute passes were planned; batch R’s pass was skipped. All runs used one NVIDIA GH200 (96 GB), batch R on a second GH200 machine, with PyTorch 2.14 and CUDA 13.0, bf16 and greedy decoding unless stated, and cuDNN attention disabled from batch 7 on (Section 5.7). Prompts are GSM8K 8-shot problems (Cobbe et al., 2021) and AlpacaEval instructions or reference texts (Dubois et al., 2024). Huginn uses HF revision bb6621b6 and Raven revision a5f6f126, both with the official modeling code unchanged. The decoder timings below use one request at a time; queueing, continuous batching and cache allocation are not measured. The supplementary appendix lists the batches and the artifact’s scope. Frozen inputs and a reconstructed runtime recipe now accompany the Huginn decoder and window-replay entry points. The pre-registration files remain outside the snapshot, so claims about their timing rely on the authors’ record. Figure 3 summarizes the three measurements that frame the rest of this section.

5.1 Generation fidelity and the tail

Huginn: mostly a precision change, plus a tail. The pre-registered statistic is KL(L0∥deepest)/KL(L0∥fp32) per bin of generated position with a prompt-paired bootstrap. On 48 confirmatory prompts the label is “exceeds a precision change”, through a single bin (ratio 13.8 [2.28, 21.2]) in which one problem carries 75% of the KL; other bins have ratios 1.6–3.3. Over all positions the median KL is lower for the deepest plane than for fp32 (6.4×10−5 vs. 8.2×10−5) but the mean is 5.7 times higher, because 1% of positions carry 74% of the KL (fp32: 21%; Figure 4a). The 9 positions with KL above 0.1 (fp32: 1) lie in 4 prompts, 5 of them in one GSM8K problem at nearby positions (Figure 4c). Only 2 of them have a reference top-2 probability margin below 0.1, where 8% of all positions lie: near-ties are over-represented (0.7 expected, 2.7×) but account for a minority of the tail. The largest value, 5.05, is one of those two.

Raven: indistinguishable from a precision change. On the same 72 prompts, Raven’s deepest plane is “indistinguishable from a precision change” on both prompt sets (bin ratios 1.04–1.51), its largest KL is 0.020 (fp32: 0.014), no position exceeds 0.1, and it flips the top-1 token at 48 positions against 76 for fp32. We had predicted the opposite, a larger effect than on Huginn; the ripening model accounts for the difference after the fact (Section 3.2).

RIPE windows remove most of Huginn’s tail. Batch 8 replayed 48 of these prompts through RIPE caches (Table 3, Figure 4b). The pre-registered count of tail positions falls from 9 to 1 at W=64 (89% fewer; ratio 0.11 [0.00, 0.20], wide because four prompts carry all tail positions), and the largest KL from 5.05 to 0.13, below the fp32 replay’s 0.23. On the problem of Figure 4c, W=16 already cuts the peak to 0.97 and W=64 to 0.13. Keeping four attention-sink positions (Xiao et al., 2023) at full depth does nothing, and neither does a second stored plane at similar memory. A post hoc prompt-level audit finds that the affected prompts fall from 4/48 to 1/48; leaving out any one prompt gives a tail-count reduction of 85.7%–100.0%. This is a sensitivity diagnostic, not a confidence interval or evidence of generalization. The 48 reference trajectories were bitwise identical to batch 7’s, on another node. This replay result is what motivated the window; Section 5.3 tests whether it survives in a decoder.

5.2 Self-speculative decoding

Batch 8 ran a real greedy self-speculative decoder on Huginn: depth-4 drafts, four per block, and one 32-loop verification pass per block. With the full cache it accepts 3.34 tokens per verification on GSM8K and is 2.09× faster than sequential decoding; with the deepest plane, 4.47 and 2.58× (Sections 3.3–3.4 model both).

With the deepest plane, batched verification depends on where blocks start (Section 4). The pre-registered test compares verification targets of batched and sequential deepest-plane decoding at identical contexts, against the same comparison for the full cache, where the two are equal in exact arithmetic. A tiny CPU model checks the implementation within numerical tolerance; the GPU comparison supplies the bf16 numerical baseline. The ratio is 1.37 [1.20, 1.62], below the pre-registered threshold of 2 (label “indistinguishable from numerics”; we had predicted 3–30), and 28 of 32 batched trajectories equal the sequential ones. On Huginn the block dependence is therefore small; Proposition 1 removes it by construction.

Using WaveFront’s released code (Ha & Kim, 2026) unchanged, batch 5 reproduced its Huginn numbers on GH200: speed-up 2.64× at acceptance 0.878 without sharing and 4.14× at 0.965 with one shared slot.

5.3 RIPE under emulated storage

Batch R implements Algorithm 1 with a per-query window and runs it, pre-registered, on the prompts of batch 8 (Table 4). Storage is emulated: the cache still holds every plane and attention reads them by πRIPE, so the batch measures decoding behaviour and batch-size-one timing, not memory or serving throughput (Eq. (10) gives the calculated memory). On a tiny CPU model, batched and sequential RIPE produce identical token trajectories when W≥γ; their stored log-probabilities agree within the test’s 10−10 absolute tolerance. The tests use fp64 model arithmetic but cast logits to fp32, so they check the implementation rather than prove exact equality. A W<γ case gives different rows. On the GPU the observed difference is compatible with the bf16 numerical baseline: the batched-versus-sequential ratio is 1.24 [0.99, 1.57] times the full cache’s floor (label “indistinguishable from numerics”), and 19 of 22 trajectories equal sequential RIPE.

Drafts decide the acceptance. Drafts that follow πRIPE read shallow, unripe planes for the recent window and accept like the full cache (3.42 tokens per verification); drafts that read plane R keep 88% [79%, 97%] of the deepest plane’s gain (4.32 against 4.46, label “keeps the shared gain”). That decoder runs 2.33× faster than sequential full-cache decoding. Sequential RIPE runs at 0.88 of sequential full-cache speed because the emulation assembles planes on every call; against it, the decoder measures 2.66×, where the cost model of Section 3.4 predicts 2.59× (pre-registered check). Post hoc, the same model predicts the full-cache and deepest-plane decoders of this run at 2.07× and 2.61× over sequential full-cache decoding against measured 1.87× and 2.77×, so its error on this machine is up to 10%. Along their own trajectories, the verification targets of RIPE(64) and of the deepest plane are not distinguishably different in their distance from the full cache on these 22 problems (ratio 0.80 [0.39, 1.25], label “no difference”; we had predicted closer), with 1 against 3 positions above KL 0.1 but a larger maximum (0.94 against 0.53). RIPE is also slower (2.33× versus 2.77×) and larger in calculated storage (341 MB versus 173 MB at L=1024). The confidence interval includes both a reduction and an increase; it does not establish equivalence. These KL values compare each arm to a full-cache reference on that arm’s own contexts, not on one common trajectory, and are not a task-accuracy equivalence test. The replay tail reduction therefore has not translated into an established end-to-end quality gain: on Huginn the window is ineffective as a repair, and it costs speed (2.33× against 2.77×) and 168 MB per sequence of calculated storage. The run stopped after 22 of 32 problems, before AlpacaEval, and skipped its Nsight Compute pass.

5.4 Pretrained Ouro: the prompt lies outside the window

Ouro-1.4B (Zhu et al., 2025) has R=4 loops over 24 layers and its own report on KV sharing: for decoded tokens, keeping the last loop’s KV is nearly lossless, but sharing it across the prompt costs more than ten GSM8K points. We ran RIPE on the pinned official Ouro classes through a physical ring-buffer implementation of Eq. (10) (supplementary appendix), first on a fixed 20-case numerical qualification and then on a task diagnostic. In the qualification, physical and emulated storage agree bitwise in all 16 RIPE cases on an L40S and again on an RTX PRO 6000, so the implementation realizes the policy. The sequential-versus-batched verification gate, however, fails in all 16 bf16 cases on both GPUs (argmax disagreements in two) and passes in all 16 when the same plan is rerun in fp32 with TF32 disabled, which places the discrepancy with bf16 execution shape rather than with the cache (Section 5.7).

The task diagnostic (Table 5) re-encodes 24 GSM8K questions that earlier batches had already used and lets each method generate until EOS or 2048 tokens. The full cache and FlashLoop’s default KIVI reader (Yang & Liu, 2026) finish 23 of 24 answers; RIPE finishes none at W=16 and two at W=64, one of them a 38-token answer identical to the full cache’s, and 23 and 19 of its capped outputs end in near-verbatim repetition. Replaying the first question’s capped W=16 and W=64 outputs teacher-forced through physical and emulated storage gives bitwise equal logits at all 2048 positions, so the repetition is the policy’s, not a ring-buffer defect (an error in the substitution code common to both paths is not excluded). The explanation is positional: the chat-template prompts have 318–415 tokens, so with W≤64 at least 80% of each prompt is read at the deepest plane, which is exactly the prompt-side sharing that Ouro’s authors found harmful. The window protects the positions being decoded, but on this model those are not the positions that matter. Earlier 160- and 512-token runs of the same questions are retained as diagnostics; none of these runs is a matched-memory or accuracy benchmark, and a variant that keeps every plane of the prompt was not tested.

5.5 Fixed-memory throughput

Batches 6 and 8 placed WaveFront’s scheduler and draft-then-verify under a 95 GB budget at the measured acceptance rates (Figure 5c): one shared slot is 2.24× (batch 6) and 2.26× (batch 8, another node) faster than the best full-cache configuration, through a larger batch and a cheaper step (Section 3.5). Two pre-registered memory predictions failed; the memory model reproduces both cells. On Huginn a one-slot cache is not lossless (Section 5.1), and RIPE was not run under this scheduler, so these figures are context for the memory stakes, not a measurement of RIPE.

5.6 What did not help

Per-head position filtering. The starting plan also proposed keeping, per head, only the prefix positions that a shallow loop attends to. Batch 1 found cross-depth attention affinity real but mostly static (sink plus recent tokens). Batch 8 froze a per-head policy from batch 1 and tested it on 64 unseen AlpacaEval texts at a budget of 10% of the prefix: filtering costs 72 times more KL than deepest-plane storage, the two costs add (ratio 0.88), and the per-head policy is 1.88× worse than top-k for every head [1.65, 2.20]. Selecting at loop 4 instead of 2 cuts the cost to 0.33 of its value, consistent with ripening.

Sinks and a second plane. Neither removed any of Huginn’s tail positions (Table 3); a recent window did.

5.7 Reproducibility on GH200

Batch 4 found that the bf16 full-cache reference was not reproducible: a same-process rerun matched bitwise at only 30% of positions, with mean KL 1.6×10−4, about two thirds of the bf16-to-fp32 floor. PyTorch’s deterministic mode did not remove it; batch 6b traced it to cuDNN’s scaled-dot-product attention (cuDNN 9.24). With that backend disabled, reruns are bitwise identical (100% of positions, across processes and nodes) and decoding is not slower; the deepest-plane labels and ratios were unchanged. Separately, WaveFront’s decoder and its autoregressive baseline produce identical texts on 31/40 problems without sharing, with cuDNN disabled or not, and our own full-cache batched and sequential decoders, equal in exact arithmetic, agree on only 20 of 32 trajectories in bf16. Computation shape alone flips bf16 trajectories at this rate, so a “lossless” claim for speculative decoding in bf16 needs a stated reference computation.

This result is limited to the tested GH200 environments; the released nocudnn setting does not pin one attention kernel, and our records do not establish cross-device bitwise equality. A replication should match model, tokenized inputs, per-position initialization and software versions, then check same-device repeatability before comparing cache fidelity or timing against a sequential baseline on the same device.

6 Related work

Looped models. Huginn (Geiping et al., 2025), Ouro (Zhu et al., 2025) and retrofitted recurrence (McLeish et al., 2025) train or convert models that iterate a core block. Ouro reports that keeping only the last loop’s KV for decoded tokens is nearly lossless on its model, whereas sharing it across the prompt costs more than ten GSM8K points; we measure when deepest-plane reuse holds and why it fails on Huginn. WISE (Wan & Chen, 2026) finds that attention routing stabilizes early in depth and reuses the early loops’ attention support; we find that later loops are more sensitive to prefix keys and values and reuse the last loop’s planes. Both exploit convergence across depth, in opposite directions.

Self-speculation in looped models. Huginn’s zero-shot self-speculation (Geiping et al., 2025), LoopSpec’s pipelined branches (Cho et al., 2026), WaveFront’s diagonal schedule with cross-recurrence KV sharing (Ha & Kim, 2026), Mature-Spec’s mature values for shallow drafts (Li et al., 2026) and LoopAhead (Liu et al., 2026). Self-speculation by layer skipping in standard models is Draft&Verify (Zhang et al., 2023); the acceptance model is that of Leviathan et al. (2022) and Chen et al. (2023).

KV compression. For standard transformers: attention sinks and streaming windows (Xiao et al., 2023), quantization (Liu et al., 2024) and paging (Kwon et al., 2023). Along the loop axis, LLA learns a latent codec (O’Neill & Reid, 2026), ResidualQuant quantizes loop residuals (Kim et al., 2026), FlashLoop combines sparse updates with residual quantization (Yang & Liu, 2026), and HLA keeps a recent exact window and reads older positions through trained latents (Chen et al., 2026). The recent-window pattern is thus shared prior art; RIPE is its training-free member, and our result is that the window alone does not repair the deepest plane. These methods’ compression levels come from different models, metrics and stacks, and we do not compare them at matched memory; the one same-model comparison we have (Table 5) is unmatched in memory and shows FlashLoop finishing answers that RIPE does not.

7 Limitations and conclusion

Limitations. The negative result rests on three models and small samples: 22 GSM8K problems in the Huginn decoder run, 48 prompts in its replay with four prompts carrying the tail, 72 prompts on Raven, and 24 reused questions on Ouro. Only greedy decoding on GSM8K and AlpacaEval is covered, and the Ouro task runs are a diagnostic with unmatched memory budgets, not an accuracy benchmark; an unfinished output is not established wrong. Batch R emulates storage, so its memory is calculated and its timing is batch-size one; no serving throughput for RIPE is measured. We did not test a window that also keeps the prompt’s planes, nor W between 64 and the prompt length, so the result bounds recent-window repair at the sizes a ring buffer makes cheap, not every windowed policy. The ripening and sensitivity models are post hoc and fitted on Huginn and Raven only; for Ouro the explanation rests on prompt length and Ouro’s own report. The Ouro and rerun evidence comes from rented L40S and RTX PRO 6000 GPUs with regenerated trajectories, so cross-device bitwise equality is not established. Matched-memory comparisons with LLA, HLA, ResidualQuant, FlashLoop and WaveFront sharing remain open, and raw outputs of the earlier batches are not released (supplementary appendix).

Conclusion. A recent full-depth window is the natural repair for a deepest-plane KV cache, and on the model that motivated it, it repairs the metric that motivated it, not decoding. On Raven the deepest plane needs no repair; on Huginn the repaired cache is slower, larger and no closer to the full cache in a real decoder; on Ouro the positions that need repair are the prompt’s, beyond any 16–64-position window. Ripeness, measurable with one prefill per prompt, and the role of the shared positions decide the outcome; recency does not. Schedule consistency, which the window does provide, is not fidelity, and in bf16 neither is bitwise agreement. Shared-plane caches for looped models should be qualified by a ripeness test and a prompt-side check before any windowed repair is considered.

B.1 Physical-cache reference implementation

The supplemental compact_ripe.py implements persistent storage separately from the frozen measurement code. It keeps one full-length plane for each prelude, core and coda layer, and a ring for each non-final recurrence of each core layer. With reserved capacity C and maximum pass length B=γ+1, the allocated tensor bytes are

Malloc=b⁡[(npre+ncore+ncoda)​C+ncore​(R−1)​min⁡(C,W+B)].(11)

Here b counts both K and V for one token and layer. The additional B slots retain the current verification block and any rejected suffix; Eq. (10) instead counts the committed-prefix policy. A pass beginning at t needs positions t−W through t+B−1, a span of W+B. After accepting k drafts, the next block begins at t+k+1, so its oldest required recent position advances and does not require restoring an evicted prefix. During prefill, attention consumes the current layer’s full K/V tensors directly and retains only their tail for non-final loops.

CPU tests compare actual reads and masks with the frozen full-plane oracle, cover every acceptance length, rejected suffix overwrites, ring wraparound, and tiny-model generation. The implementation still gathers dense attention inputs; the equation excludes their temporary storage, model activations and allocator overhead. It supports one request and has no fused serving kernel. These checks establish implementation behavior on CPU, not GPU performance.

The separate executable protocol fixes 12 cases at W∈{16,64}: four original prompt sequences and two repeated-token contexts of lengths 1024 and 4096, each generating 64 tokens without early stopping. It compares compact and emulated RIPE rows before three rotated timing trials against sequential full-cache decoding and speculative deepest-plane reuse. Prefill, decode, persistent bytes and CUDA peaks are reported separately. Synthetic contexts test storage and runtime only. An L40S run completed 10 of the 12 cases and all 120 associated timing records; all ten recorded physical/emulated numerical checks passed. The first 4096-token-prefix case then raised an asynchronous CUDA index-out-of-bounds assertion, leaving both 4096 cases incomplete. The original qualification therefore did not pass. Huginn’s configured RoPE table covers 4096 positions, whereas the first decode after a 4096-token prompt uses position 4096. A CPU check of the original table constructor confirms that this index is out of bounds; the asynchronous CUDA trace does not independently locate the offending operation. A separate post hoc run extended that table with the same formula and verified that its original entries were bitwise unchanged. For the two 4096-prefix cases, both recorded compact/emulated checks passed and all 24 timing records were present. The logged persistent KV storage was 0.759 and 0.885 GB for compact RIPE at W=16 and W=64, versus 11.614 GB for emulated RIPE. These cases use a single synthetic prompt beyond the checkpoint’s configured context; raw log-probability arrays were not retained, and they do not repair the original qualification or establish output quality or serving gains. This protocol supplies neither task accuracy nor matched-memory comparisons with other methods.

For a common-model diagnostic with FlashLoop, a supplemental adapter connects the cache to pinned official Ouro classes and changes both loop depth and output-head selection; selecting a head alone still executes all loops. Tiny-model CPU tests cover native full-cache agreement, physical/emulated rows and shallow drafts. A separate NumPy auditor recomputes numerical gates from saved output positions 2–32 and checks acceptance-schedule consistency; it cannot reconstruct the first-token or full draft-chain decisions. Separate L40S runs on pretrained Ouro are reported below; they do not constitute a matched-memory task-quality or serving comparison.

We then reran the same 24 questions with a 2048-token cap, stopping only at EOS, with all four methods for each question on one GPU (12 questions on two L40S, 12 on two RTX PRO 6000; within-GPU pairing only). Full cache and FlashLoop reached EOS on 23 of 24 questions, RIPE W=16 on none and W=64 on 2; one of these is a 38-token answer identical to the full cache’s.
