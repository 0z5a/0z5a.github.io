1 Introduction

Looped, or recurrent-depth, language models reuse one block of transformer layers several times for each token. Huginn-0125 runs a four-layer block 32 times between a short prelude and coda Geiping et al. (2025); Ouro runs all of its layers four times and can exit early Zhu et al. (2025). Depth becomes a run-time knob, which makes these models attractive for reasoning at a fixed parameter count. For a serving engine a looped model looks like a much deeper model whose layers share weights. The natural first optimization is to fuse the loops of a decode step into one GPU submission, which removes host round trips that grow with depth.

We tried this on vllm-rlt InferMatrixLab (2026), an open-source engine built for looped models (main branch at commit 66920da), and it did almost nothing at low load. On an RTX 5090, fusing Ouro’s four loops halved the submissions per token (6.0 to 3.0) and left batch-1 throughput at 0.99×; it helped only at higher load (1.09× at 32 requests). The loops are not the problem. The problem is that every per-layer cost is paid once per loop, so small costs that a conventional engine can ignore become large. We found two that matter most.

Dead KV slots. The engine keeps a separate KV plane for each recurrence depth, so that a token at depth d attends to keys computed at depth d. Each plane reserves a slot for every layer. In Huginn only the four recurrent layers write deeper planes; the four prelude and coda layers write plane 0 only. Of the 8×32=256 layer slots a token reserves, 124 are never written. On a GH200 the base engine therefore stops scaling near 65 tokens/s, because only a few dozen requests fit in the KV pool. The same layout breaks prefix caching: the cache publishes a prefix only when every layer of every plane has written it, which never happens for Huginn.

Kernel count. At batch 1, an Ouro token costs 5689 GPU kernels on a GH200, most of them small elementwise and reduction kernels from RMSNorm, rotary embedding (RoPE) and the gated activation, each repeated for 24 layers and four loops. CUDA graphs remove their launch cost but not their minimum run time. Fusing them is the obvious remedy, but fused kernels round differently, and in a recurrent model a one-ulp difference passes through 96 layer applications. Our first fused kernels changed GSM8K answers.

The exactness ladder. An optimization for a deployed model is easier to adopt the less it changes outputs. Table 1 records what each ExactLoop change preserves at two levels: the arithmetic applied to the same inputs and batch, and the tokens observed after deployment. A r0 change is bitwise identical under the same batch composition. It may change capacity or scheduling, which can in turn expose the batch-size-dependent arithmetic called r1; an end-to-end comparison then contains both effects. r1 changes preserve each row’s operations but change the rows that share a batch, so GEMM algorithms can flip bits He (2025). r2 changes target the same sampling distribution with different random numbers. r3 changes alter arithmetic and need a task-level accuracy check. Rungs 0 and 1 produce the Huginn high-concurrency and Ouro batch-1 gains. Long-prompt and session gains come mainly from rungs 2 and 3, while the PD gain is split between rung-3 packed prefill and a rung-0 transfer budget.

  • A characterization of a looped-model engine that traces Huginn’s throughput ceiling to dead KV slots, Ouro’s batch-1 latency to kernel count, and Huginn’s zero prefix-cache hit rate to the publication rule and to order-dependent recurrent-state noise (Section 3).
  • Plane packing, which stores only live layer slots and holds 1.88× more Huginn tokens in the same pool with bitwise-identical outputs under the same batch composition (Section 4.1).
  • Exact kernel fusion: fused RMSNorm, RoPE and SiLU kernels that are bitwise identical to PyTorch because the row sum keeps PyTorch’s order and rounding fences, inline PTX conversions the compiler cannot see through, pin every rounding point on the tested PyTorch, CUDA and GPU configurations (Section 4.2).
  • Position-keyed recurrent-state noise, which makes Huginn’s random initial state a function of (seed, position, channel), so a cached prefix sees the same noise as a cold run independent of draw order (Section 4.4).
  • An evaluation that reports token-level matches alongside throughput and latency, covers two GSM8K check sizes, real prompts under Poisson arrivals and a third model, and documents four negative results: approximate fusion, speculation at high load, eager-mode kernel launch cost, and a KV transfer paced by engine polling (Sections 5 and 6).

Contributions. The supplementary appendix lists every GPU batch we ran, the question it asked and its outcome, including the batches that produced no data and the ones that refuted our own explanations.

Most of the individual techniques have precedents: paged KV layouts, kernel fusion, counter-based random numbers and transfer budgets. What this paper adds is their measured effect on looped models, and an exactness grading that decides which of them can be shipped without an accuracy check.

2 Background

Looped models. Ouro-1.4B has 24 transformer layers that run four times per token; a learned gate can stop a token early Zhu et al. (2025). We run it at a fixed depth of four. Huginn-0125 embeds a token, runs two prelude layers, initializes a latent state with truncated normal noise, applies a four-layer recurrent block 32 times to the state and the prelude output, and decodes the result with two coda layers Geiping et al. (2025). Earlier weight-shared models include Universal Transformers Dehghani et al. (2019); early-exit models such as CALM Schuster et al. (2022) and LayerSkip Elhoushi et al. (2024) also vary depth per token.

The engine. vllm-rlt extends paged KV caching Kwon et al. (2023) and continuous batching Yu et al. (2022) to looped models and implements runtime ideas from continuous depth batching Schwethelm et al. (2026). A request moves through PREFILL, PRELUDE, RECURRENT and CODA phases, and the scheduler forms each batch from rows in one phase. In the LAST_EXITED layout every recurrence depth has its own KV plane, a token at depth d attends to plane d, and a row that exits early copies its last plane forward. The engine supports asynchronous scheduling, CUDA graphs for decode, Triton Tillet et al. (2019) paged attention, a prefix cache, self-speculative decoding with a shallower draft Zhang et al. (2024), and prefill–decode (PD) disaggregation Zhong et al. (2024); Patel et al. (2024) that writes KV pages into the decode engine’s pool with NIXL NVIDIA (2025). Prefill runs one row at a time by default; a packed, variable-length prefill path exists but is opt-in.

3 Per-Loop Overheads, Not Loop Arithmetic, Set the Speed

We profiled the base engine with random-token burst workloads (all requests arrive at once, greedy decoding, fixed depth) and with multi-turn agent-session traces (Section 5.1).

Loop submissions do not limit batch-1 decode. On the RTX 5090 an Ouro token at batch 1 took 16.2 ms. Fusing its loops cut the submissions per token from 6.0 to 3.0 and the per-step host time several-fold, yet the time per output token (TPOT) stayed at 16.3 ms. A kernel profile on the GH200 explains why: 5689 kernels and 13.05 ms of GPU time per token. With graphs the host no longer launches these kernels, but each still runs for a few microseconds. Each RMSNorm is eight kernels in PyTorch Paszke et al. (2019), four norms per layer.

Dead KV slots cap Huginn’s concurrency. For each Huginn token, upstream reserves 5.41 MB of KV, of which 2.79 MB is ever written. On the RTX 5090 the pool held 1328 tokens, two requests of our burst, and throughput stayed at 17.8 tokens/s from 8 to 64 concurrent requests (16.7 at 64). On a GH200 the pool is larger but the effect is the same: the base engine’s throughput stayed near 65 tokens/s from 32 requests on (Table 2).

Cache hits follow KV capacity, and Huginn publishes no prefix. Ouro sessions on the GH200 reused 79.5% of prompt tokens from the prefix cache with 32 sessions but 24.8% with 64, whose working set exceeds the 98,336-token pool. On the RTX 5090, whose pool holds 24,480 tokens, the hit rate fell from 45.7% to 10.7% to 2.4% for 16, 32 and 64 sessions. Huginn never hit at all: the cache publishes a page only when every layer of every plane has written it, and Huginn’s boundary layers never write planes 1–31.

Prefill runs one row at a time. With 2048-token Ouro prompts, packed prefill was 2.42× and 2.00× faster than the per-row default at 8 and 32 requests, with 61% lower time to first token (TTFT) at 32.

KV transfer stalls behind prefill. In a one-prefill, one-decode deployment on two GPUs of one GH200 node, the base engine at 32 requests spent a median of 2.85 s per request between the end of prefill compute and the last KV chunk leaving (the commit tail), as long as the prefill compute itself (2.87 s). The transfer ran at 1.44 GB/s.

4 ExactLoop: Removing the Overheads, Graded by Exactness

4.1 Packing live slots changes addresses, not values (r0)

Packing gives each depth plane only the layer slots that it can hold (Fig. 1). A KV page becomes a run of blocks, each with num_layers slots, and slot s of block b is entry b⋅num_layers+s of a flattened view of the pool. Plane 0 maps all eight layers; planes 1–31 map the four recurrent layers. A Huginn page then needs 17 blocks instead of 32. Attention, KV writes, early-exit plane copies and the asynchronous finalize kernel take an entry stride and a first-layer offset instead of assuming a full plane. The PD transport sends each plane’s live slot range, and the PD coordinator prices requests in blocks per page. Values never change, only their addresses, so outputs are bitwise identical. For models without boundary layers, such as Ouro, the layout is unchanged. These checks assume equal inputs and equal batch composition. When packing admits more requests, the scheduler also changes the batches; we report those token comparisons separately in Section 5.4.

4.2 Rounding fences make fused kernels bitwise (r0)

PyTorch computes a bf16 RMSNorm as a chain of eight kernels: cast to fp32, square, mean, add ϵ, rsqrt, multiply, cast to bf16, and multiply by the weight, plus an addition when a residual is fused. A one-kernel Triton version differs from it in two ways. It sums the squares in a different order, and its compiler moves rounding points. We keep both under control.

Keep PyTorch’s summation order. The exact RMSNorm sums the squares in PyTorch’s order. Its first form leaves the mean to PyTorch between a Triton square kernel and a fenced Triton tail for rsqrt⁡(x¯+ϵ) and the scaled output (Triton’s rsqrt lowers to PyTorch’s instruction; x¯+ϵ is one IEEE addition). PyTorch 2.14’s mean fixes its order by its launch configuration (W lanes per row set by the row count, four strided accumulators per lane, a halving tree); for Ouro’s and Huginn’s widths the second form repeats those additions in one kernel, and shapes PyTorch would split across warps keep three kernels.

Fence the roundings. Writing the same casts as PyTorch is not enough. Triton and LLVM keep an fp32 product live across a cast to bf16 and back (.to(bf16).to(fp32)), and contract a⋅b+c into a fused multiply-add. Our first fused residual epilogue therefore computed round⁡(r+w⋅n) while PyTorch computes round⁡(r+round⁡(w⋅n)), a double rounding Higham (2002). On 75,776 bf16 elements, 18.4% differed from PyTorch by one ulp, and 0 differed from a single-rounding oracle. A rounding fence is an inline PTX instruction, cvt.rn.bf16.f32 or mul.rn.f32, that performs one IEEE rounding the compiler cannot see through, so it can neither drop nor merge it. The exact RoPE kernel fences each of its two products before adding them. The exact SiLU-and-multiply kernel fences silu⁡(g) before multiplying by the up projection; its exponential comes from the same CUDA math library that PyTorch links. For the residual addition we use PyTorch’s own addition.

Fuse only inside graphs. On the GH200’s Grace host a Triton launch from Python costs more host time than the PyTorch launches it replaces. Under CUDA graphs that cost is paid once at capture; in eager prefill it is paid on every call. ExactLoop therefore uses the fused kernels only while a CUDA graph is being captured, which covers decode, and leaves eager code paths on PyTorch.

4.3 Loop fusion changes only which rows share a batch (r1)

Rows decoding at a fixed depth run all their loops in one submission, which replays one graph for L loops. On the GH200 this cut Ouro’s submissions per token from 5.9 to 3.0 and Huginn’s from 17.7 to 3.0 at 8 requests. Each row’s arithmetic is unchanged: with one request at a time, GSM8K token sequences matched on all 87 questions. The batches are not unchanged. The base engine staggers rows across loop phases, while loop fusion runs them together, so GEMMs see different batch sizes, cuBLAS may pick different algorithms, and some bf16 outputs change at high load: 202/208 requests matched the base engine at 8 to 64 requests, while two runs of the base engine matched on 208/208. That makes it r1.

A fused step is L loops long, and the scheduler admitted a fixed number of prefill batches per decode step. Prefill was therefore admitted L times less often per unit of decode work, and TTFT grew under load (Section 5.7). ExactLoop admits up to L prefill batches after an L-loop fused step, which restores the base engine’s ratio of prefill to decode work per loop.

4.4 Per-plane coverage makes prefixes reusable; position keys fix the noise order (r2)

We changed the publication rule so that each plane must cover only the layers that it holds. Huginn prefixes are then published and reused, but a cache hit still changes outputs. Huginn draws the initial latent state of each token from a per-request random stream, in the order tokens are processed. A request whose first k prompt tokens come from the cache draws k fewer values, so every later token receives different noise than in a cold run. The prefill chunk size changes the draws in the same way.

Position-keyed noise makes the noise a function of the request seed, the token position and the channel. A hash in the style of SplitMix64 Steele et al. (2014), applied in stages with distinct constants, turns (seed, position, channel) into a 24-bit uniform number, and an inverse normal CDF maps it onto the intended truncated normal distribution at 24-bit resolution, as in counter-based generators Salmon et al. (2011). The target distribution is the same, subject to this discretization and the inverse-CDF implementation’s rounding. 64-bit wrap-around is identical on CPU and GPU. In CPU tests, cached and cold runs, and prefill chunks of 2 and 8 tokens, produced identical tokens. A seeded run sees different samples from upstream’s sequential generator, so the feature is opt-in together with Huginn prefix caching.

On the GPU the noise is only part of the story. We ran 128 prompts of 512 tokens one at a time on Huginn-0125, cold and then again with 496 tokens served from the cache; cold runs repeated exactly (128/128). With position-keyed noise, 108/128 cached runs matched the cold run token for token (95% interval 77–90%), and a longer prompt that reused the same prefix matched in 116/128 (84–95%). An earlier eight-prompt check with the sequential generator gave 6/8 full hits; there, position keys fixed the one prompt that changed at its first token. The remaining divergences come from prefill arithmetic: a cached run prefills only the suffix, so its GEMMs see fewer rows, and changing only the prefill chunk size also changed outputs (220/256 cold runs matched between chunks of 2048 and 128 tokens). On the GPU, prefix reuse therefore behaves like a change in batch composition (r1) layered on a r2 change of samples. The noise itself is not negligible at 32 loops: the two generators gave the same tokens for only 177/256 cold runs. Position keying removes one source of cache dependence without making all GPU cache hits token-identical.

4.5 Packed prefill and its accuracy check (r3)

The engine resolves packed prefill at construction: it turns it on for CUDA, the LAST_EXITED layout, refill scheduling and a backend with a packed path, and an explicit setting always wins. Packed bf16 prefill computes attention with different arithmetic than per-row prefill, so a few greedy sequences change (Table 1). For Huginn, whose boundary layers need their own attention metadata, packed prefill changed the full GSM8K split by −0.61 points (Section 5.8), within the one-point rule only on its point estimate. The packed path stages its inputs in host-mapped pinned memory (UVA) instead of copying them to the GPU.

4.6 The PD fixes change no values (r0)

The upstream PD coordinator built every model with Ouro’s configuration class, so a real Huginn checkpoint could not start; it now picks the class from the model type the worker reports. With packing, the transport sends only live slots, 0.516 of the full Huginn layout. Descriptors that are contiguous on both sides are coalesced, and an overlap counter now credits transfers issued during a prefill computation. The connector can also create its UCX Shamis et al. (2015) backend explicitly with an error-handling mode, and the default transfer budget now holds one long prompt’s KV in flight (Section 6).

5 Evaluation

5.1 Setup

Platforms. We used three machines. A batch-scheduled GH200 system ran single-GPU jobs and the two-GPU PD jobs, with PyTorch 2.14, Triton 3.8 and NIXL 1.4.1. A standalone GH200 host, whose GPU our runs held exclusively, ran the release table, the accuracy gates and the end-to-end and Huginn session comparisons. A rented RTX 5090 ran the first characterization. Every speedup compares arms run on the same machine.

Workloads. In a burst workload, C requests arrive at once, each with a prompt of 512 or 2048 random tokens and a fixed number of greedy output tokens. Session workloads replay multi-turn traces of a coding agent SemiAnalysis (2026) whose prompts grow with the conversation, with n concurrent sessions and the prefix cache on. Ouro runs at depth four with asynchronous scheduling and CUDA graphs unless noted; Huginn runs at depth 32 with CUDA graphs and synchronous scheduling, which the engine requires for it.

Configurations. Table 2 measures the released defaults (loop fusion with the prefill share, plane packing, exact kernels in graphs and in eager calls over 256 rows, automatic packed prefill) against the base engine, three runs per cell. ExactLoop evolved during the study, so the component tables that follow state which features their arms had; unless they say otherwise, their ExactLoop arm prefilled one row at a time and had no prefill share.

Noise. Apart from Table 2 and the arms that say so, cells are single runs. On the standalone host two runs of the base engine at 32 requests differed by a factor of 0.84, and the first repeat of an arm ran 17% below its later repeats (up to 33% for session arms). Where an arm has repeats we drop the first; we treat differences within the rerun spread as ties. Several gains reported below, such as the graph-count and packing ratios, lie within or close to this band and are presented as directional. Token identity compares each request with the request of the same level, repeat and index.

Run-to-run variation. The headline cells retain two runs after warm-up, while several component experiments have only one. Host and scheduling variation can therefore obscure small differences. We discuss component effects only when they exceed the observed rerun spread and leave the remaining measurements as directional. Section 5.8 treats the accuracy subset separately because its sample size differs from the performance runs.

5.2 The released defaults are 1.6–3.2× faster than the base engine

Table 2 is the headline result. Figure 2 plots it. With 512-token prompts the released defaults serve Ouro 1.65–2.15× and Huginn 1.77–3.16× faster than the base engine, and both time to first token and time per output token fall at every load. With 2048-token prompts, where packed prefill dominates, Ouro runs 1.91–2.04× faster. Huginn’s median TTFT at 64 requests falls from 22.7 to 4.0 s. Packed prefill and batch composition change some greedy sequences: 285/315, 109/120 and 271/315 requests are identical to the base engine.

On the batch-scheduled GH200, with Ouro and Huginn on different builds, the same workloads gave the same token identity but larger Ouro gains (2.0–2.3× and 3.5–3.8×) and Huginn gains of 1.5–2.7×: the speedups depend on the platform. The base engine’s batch-1 Huginn throughput also moved by 17% between two batches, so the batch-1 Huginn ratio is the least certain of these headline numbers.

On the batch-scheduled host, in four interleaved rounds per arm, the released defaults served Ouro agent sessions 1.91× and 3.21× faster than the base engine at 32 and 64 sessions, with a median TTFT of 0.15 instead of 1.98 s at 64, and Huginn sessions 2.72× faster with the prefix cache (Table 3); Table A5 takes the Ouro gain apart.

5.3 Real prompts under Poisson arrivals

We replayed ShareGPT and Alpaca prompts with each reference answer’s length, offline and under Poisson arrivals, on the standalone host and the same two trees (Fig. 3). Offline, with 64 requests at once, they were 1.71× (ShareGPT) and 1.29× (Alpaca) faster for Ouro and 2.01× and 1.60× for Huginn; Alpaca’s answers average 58 tokens, so admission weighs more. Online, Huginn’s latency per token was 2.9–4.2× lower at every rate, and its ExactLoop arm had not saturated at 1.5 requests/s. Ouro’s base engine saturated first: its latency per token rose 4.3× from 2 to 4 requests/s, while ExactLoop stayed at 0.041 s at 4 (base: 0.054 s at 2) and was 2.3× lower at 6. From 8 requests/s both were saturated at the same throughput (343–386 against 308–390 tokens/s), so that ceiling lies in what ExactLoop leaves unchanged; we did not trace the step mix. Median TTFT was higher with ExactLoop at 1 of 6 Ouro and 2 of 5 Huginn rates. Ouro-2.6B (48 layers, same shapes) ran 2.0–2.3× and 2.2–3.3× faster on the release workloads (272/315 and 67/120 identical) and 1.68× on ShareGPT. 2 of 10 Poisson runs of Ouro’s released defaults aborted, in a cuBLAS GEMM writing to an unmapped address; the cause is open.

5.4 Packing lifts Huginn’s ceiling; loop fusion carries batch 1

Table A1 isolates packing on an earlier tree. The same pool holds 12080 tokens unpacked and 22736 packed. At 8 requests both layouts fit and run alike (1.01×); at 32 and 64 requests packing raised throughput 1.21× and 1.28×, and at 64 requests it cut the median TTFT from 10.8 to 5.5 s. 309/312 requests matched: packing changes no value, but when more requests fit, the batches differ, as with loop fusion. In an earlier tree with per-row prefill, where the batches did not change, all 233/233 requests matched. The first GH200 batch measured smaller gains of 1.14× and 1.16× at 32 and 64 requests (ledger item 10). We report the repeated earlier-tree measurement above, and the lower values lie within the rerun spread.

At one request capacity does not bind, so the batch-1 gain of Table 2 comes from the other changes. In one batch on that tree, the fused kernels contributed only 1.00×, 1.07× and 1.03× at 1, 8 and 32 requests (full set over kernels disabled, three runs each, first dropped): Huginn’s layers are large and few, so kernel count matters little, and at one request the remaining changes are loop fusion and the host path. Against a base-engine arm from a later batch the full gain was 1.59×, 1.92× and 2.57× on the standalone host (1.77× at one request in Table 2); the base engine’s batch-1 Huginn speed moved by 17% between two batches. Its 32 loops make submissions matter more than for Ouro: at 8 requests the base engine needed 17.7 submissions per output token and ExactLoop 3.0. Packed prefill helps Huginn as much as Ouro: at 32 requests it was 1.33× faster with 512-token prompts and 2.08× with 2048-token prompts, where it cut the median TTFT from 41.9 to 18.1 s (single runs).

5.5 Prefix caching makes Huginn sessions 1.16× faster on top of ExactLoop

Prefix caching with position-keyed noise reused 78% of prompt tokens and raised Huginn session throughput 1.16× over ExactLoop without the cache, which was itself 2.34× the base engine (Table 3); together 2.72×, with the median TTFT cut to 1/15. The base engine ran alike with 16 and 64 graphs (14.0 tokens/s), and no Huginn session run fell back to eager execution. On an earlier tree the prefill share made no measurable difference here. On the batch-scheduled host an earlier tree gave 3.12× with the prefix cache.

5.6 Exact fusion matches approximate throughput

With the three-kernel RMSNorm the exact set cut kernels per token from 5689 to 2885 at batch 1, a 49% reduction, and GPU time per token from 13.05 to 8.91 ms. With the one-kernel RMSNorm it raised throughput 1.55×, 1.59×, 1.51× and 1.11× at 1, 8, 32 and 128 requests, against 0.97–1.30× with the three-kernel norm (Table A2), and 1014/1014 requests matched the unfused arm. The approximate set, whose RMSNorm sums in its own order and which has no fences, was no faster within the host’s spread (1.23–1.67×) and left only 894/1014 requests unchanged. ncu on the three-kernel form shows why kernel count, not kernel work, sets the batch-1 time: its four exact kernels ran 2.4–3.8 μs each and reached at most 0.2% of DRAM throughput. The exact set therefore costs no measurable throughput in this experiment. We discuss its accuracy result in Section 5.8.

Table A3 shows why fusion was first limited to graphs: fused kernels in every scope made eager prefill slower than the base engine’s at all three levels, and graph-only fusion made it faster. Its throughput columns are single runs within the rerun spread, so we use only its prefill times. Packed prefill makes eager calls large, though: the exact kernels in eager calls over 256 token rows cut Ouro’s prefill GPU time by 29% and Huginn’s prefill time by 14% at 64 requests and raised throughput up to 1.06× (Ouro, 2048-token prompts) and 1.05× (Huginn). Fusing Huginn’s own activation and rotary embedding added 1.07–1.11×, and the one-kernel RMSNorm, 2.0–4.4× faster per norm in CUDA graphs and bitwise in all 156 GPU test cases, added 1.13–1.17× for Ouro and 1.06–1.08× for Huginn. Running Ouro’s q/k/v and gate/up projections as one GEMM each over concatenated weights (seven GEMMs per layer and loop to four) is bitwise on this cuBLAS for each of rows 1–8192, eagerly and in graph replay (not on an L40S, so only checked GPUs fuse); it cut decode GPU time at one request by 12% and added 1.06–1.12× (512-token prompts) and 1.07–1.08× (2048). No request changed in these arms; Table 2 includes them.

5.7 The prefill share trades time per token for time to first token

Table A5 shows a trade-off. With 64 sessions, ExactLoop without the prefill share and with per-row prefill cut the median TPOT from 0.99 to 0.43 s but raised the median TTFT from 1.95 to 3.44 s, because fused decode steps delayed prefill admission (Section 4.3); we compare against the 64-graph base engine, although its median TTFT was higher than with 16 graphs (1.48 s), which we cannot explain. Packed prefill raised throughput to 2.79× the base engine and brought the median TTFT down to 0.94 s. With 2048-token bursts, packed prefill was 2.42× and 2.00× faster; with 512-token bursts it was within noise of per-row prefill (0.98× and 1.19× at 8 and 32 requests, against a rerun of 0.98× and 1.10×), and without UVA staging it fell to 0.88× and 0.93× (2 kept runs each).

The prefill share helps the burst case, and was ahead in both kept runs. At 32 requests with 512-token prompts (2 kept runs), it raised throughput from 877 to 1001 tokens/s, cut the median TTFT from 1.11 to 0.82 s and the p90 from 2.13 to 1.63 s, and lowered TPOT from 25.9 to 22.8 ms. In 64-session runs it is a trade-off: on top of packed prefill, the share cut the median TTFT from 0.94 to 0.25 s and the p90 from 4.25 to 1.15 s, but raised the median TPOT from 0.14 to 0.32 s and kept 0.88× of the throughput; with 32 sessions it changed little (0.96×). We made the share the default because TTFT is the metric agents wait on, but the choice depends on the service objective.

5.8 Accuracy checks and the approximate-kernel decision

We used the engine’s GSM8K Cobbe et al. (2021) harness on a fixed 87-question subset, greedy, one request at a time, with a regression limit of one point. On the GH200, the exact kernel set answered 62 questions correctly, as did the unfused engine, and 0 token sequences differed. On the RTX 5090, loop fusion matched the base engine on all sequences and exit depths (64 correct). The approximate RMSNorm alone scored 61 against 64 (−3.45 points, paired standard error 2.56; 29 sequences differed) and the full approximate set 62 (−2.30, standard error 1.62; 23 differed). Both trip our one-point rule. We used that rule to decide whether to ship the kernels, not as a hypothesis test; the 95% intervals, roughly [−5.5,+0.9] and [−8.5,+1.6], include zero. With 87 questions, the subset cannot separate changes of one and two points, so we repeated both decisions on all 1319 test questions on a GH200, batched (32 requests, CUDA graphs, same stops and scorer). The exact and unfused paths then matched on every sequence. The approximate set changed the score by −0.15 points (s.e. 0.55) and the approximate RMSNorm by +0.76 (0.60), within the rule; GPU, batching and reference differ from the subset. The approximate kernels stay unshipped: they are neither bitwise nor faster.

Packed prefill changed Ouro by −0.99 points (s.e. 0.56) and Huginn by −0.61 (0.48): within the rule on the point estimate, with 95% intervals reaching −2.1 and −1.5. Batch composition alone moves scores as much: with 16 requests per batch, per-row Ouro answered 816 instead of 824 and packed prefill changed it by −0.08. Batches of 64 replayed the 32-request outputs almost token for token, and Huginn’s batch 16 replayed them exactly (1319 of 1319), so Huginn has one observation and a one-point loss is not excluded. On MATH-500 (496 questions) packed prefill changed Ouro by +0.40 (1.21) and Huginn by −0.20 points (0.61), and the exact set matched unfused on all 496.

Huginn’s r2 changes were gated with all 87 questions run as one batch on the released defaults. Sequential noise answered 23 correctly, position-keyed noise 22 (−1.15 points, paired standard error 2.00), and position-keyed noise with prefix reuse 21 (−2.30 against sequential noise, standard error 1.62). Both miss the same one-point rule, although their differences are within about one and a half standard errors. The choice of noise generator alone changed 38 of 87 sequences. Since 87 questions cannot separate one- and two-point effects, we repeated the comparison on the full test split of 1319 questions. There sequential noise answered 300 correctly (22.7%), position-keyed noise 307 (+0.53 points, standard error 0.51) and position-keyed noise with prefix reuse 306 (+0.45 against sequential noise, standard error 0.50; −0.08 against position-keyed noise without reuse, which served 293k prompt tokens from the cache). Both full-split variants remain within one point of sequential noise. This result is more convincing than the subset, though it still comes from a fixed rule. As expected after a change of random numbers, most sequences differ: only 572 of 1319 were identical between the two noise generators, and 636 between position-keyed noise with and without reuse.

5.9 Speculation pays at low load; an adaptive budget avoids its high-load cost

The speculative path needs fixed-depth exits and is not available for Huginn. With enough graphs that no step ran eagerly (128, 0 fallbacks), self-speculation with four draft tokens served Ouro 1.52×, 1.37× and 1.13× the throughput of plain decode at 1, 2 and 4 requests, 1.13× at 8, 1.05× at 16 and 0.75× at 32: once the target model saturates the GPU, the draft’s extra loops are cost. Its verification rows also multiply batch shapes; this arm captured 85 graphs, and with 24 it ran most steps at 16 and 32 requests eagerly, which earlier made it look several times slower than here. On the standalone host ExactLoop’s speculative path was 1.52× and 1.31× the base engine’s at 1 and 8.

The speculative path also runs a whole token, prelude, loops and coda, in one engine step (151 steps instead of 408 for a 32-request burst). Without drafts (K=0) that alone gave 1.07–1.08× up to 8 requests and 1.01–1.04× at 16 and 32, with 126/128 sequences identical at 32 (r1). A load-adaptive draft budget combines both: with at most 8 verification rows per round, each of N ready requests drafts min⁡(4,⌊8/N⌋−1) tokens. This gave 1.52×, 1.37× and 1.26× at 1, 2 and 4 requests, against 1.13× for fixed K=4 at 4, and 1.01× instead of 0.75× at 32 (three runs per cell, first dropped).

5.10 Decode is already zero-copy; copy kernels and noise syncs remain

We counted every host–device copy, blocking synchronization and copy kernel in a window of decode steps (Table A4). The engine’s host side is already close to zero-copy. With asynchronous scheduling and graphs, decode issues no host-to-device memcpy at all, because inputs are staged in host-mapped memory and read by the kernels, and one pinned 8-byte device-to-host copy per token, the sampled token (one batched copy per step at 32 requests). In packed prefill, UVA staging replaces 3.7 host-to-device memcpys per thousand prompt tokens (27 KB) with zero; without UVA staging, packed prefill ran at 0.88–0.93× of per-row prefill (Section 5.7).

What remains is movement on the device and blocking reads on the host. At batch 1 the base engine launches 1004 copy and cast kernels per token, from RMSNorm’s casts and RoPE’s concatenations; the exact kernel set removes all but 29 of them. Huginn’s sampler is the other case. PyTorch 2.14’s trunc_normal_ rejection-samples and checks mask.any() after each round, a blocking read, and the engine calls it once per request for every token’s initial state. In a Huginn decode window ExactLoop issued 6 such blocking reads per step, 2.4 per output token, besides 12 host-side scalar conversions. Position-keyed noise computes the same distribution with an inverse CDF in one kernel (Section 4.4); in the same window it issued 0 blocking reads and 0 scalar conversions, and device-to-host copies fell from 6.3 to 0.3 per step. In two paired runs of three repeats each, it gave Huginn 1.04–1.09× the throughput of sequential noise at 32 requests, 1.01–1.04× at 8 and 0.92–1.00× at one. On the PD path, KV moves from the prefill pool into the decode pool’s final pages with no staging copy, and with packing only live slots move (Section 4.6).

5.11 Packed prefill and a larger in-flight budget raise PD throughput up to 3.3×

Table 4 compares the base engine with ExactLoop on an earlier tree. With 2 GB in flight and UCX error handling off, so that KV moves by CUDA IPC, ExactLoop served 479 tokens/s at 32 requests in all three runs against 143–147 (3.3×). This arm disables UCX peer error handling, which the base arm does not, so the ratio is not a transport-matched comparison; the error-handling arm below is the conservative one. The median TTFT fell from 11.0 to 2.0 s and the commit tail from 2.8 s to 16 ms. With NIXL’s default error handling, which keeps peer failure detection and runs over TCP, two runs reached 450–457 tokens/s (3.1×); the third reached 205 with TTFT and tail unchanged and a median TPOT of 116 instead of 21 ms, so it lost time in decode, not in the transfer. Averaged over all three runs, that arm is about 2.6× the base; Section 6 traces this signature to the CUDA graph cache. With 8192-token prompts, 6.4 GB of KV per request, ExactLoop reached 79–89 tokens/s against 13.8 and cut the median TTFT from 33.7 to 3.8–4.5 s; an 8 GB budget, one round per request, gave 86, so at this length the budget hardly matters. With two prefill and two decode GPUs ExactLoop served 610–617 tokens/s at 32 requests against 236 (446–450 with the old budget); at 64 requests its two runs gave 460 and 751, a decode-side spread like the one above. The PD and transfer-connector GPU tests passed on both trees (52 on the base engine, 56 on the PD branch).

Two changes produce the gain: packed prefill and the in-flight budget. In an earlier single run with the old budget, per-row prefill reached 157.5 tokens/s at 32 requests and packed prefill 294.4, against 129.0 for the base engine; prefill compute fell from 2.69 to 0.64 s. All arms moved the same bytes, 786 KB per prompt token, yet a 64 MB chunk took 44.5 ms behind per-row prefill and 14.5 ms behind packed prefill: the transfer speed followed the prefill step length, which pointed at the host rather than the link.

A single-run sweep of the budget (64 MB chunks and 256 MB in flight against 256 MB and 1 GB) separates the two explanations. With per-row prefill, chunks four times larger took four times longer and bandwidth stayed between 1.26 and 1.40 GB/s, so the in-flight budget was not the limit. With packed prefill, the larger budget cut the median TTFT by 48%. UCX’s own log showed that intra-node remote memory access ran as active messages over TCP on the node’s host network interface, and TCP moves data only when the host polls it. That explains why chunk time grew with chunk size behind per-row prefill, but not the whole commit tail: removing TCP left chunk times almost unchanged. With three runs each on that tree, raising the budget from 256 MB to 2 GB raised throughput 1.7× (271–308 to 479 tokens/s) and cut the tail from 1.0 s to 16 ms; Section 6 explains why.

6 Lessons and Negative Results

Approximate fusion: too few questions. The approximate kernels rounded once where PyTorch rounds twice and summed in a different order, changing some elements by an ulp or two. They changed more GSM8K sequences than the exact set and crossed our one-point rule on 87 questions, but not on the full split. Neither sample shows that accuracy fell, or that it did not fall by a point. For looped models, a per-element ulp bound is not enough evidence of harmlessness; the check needs enough questions to resolve the effect of interest.

Fused kernels cost host time in eager mode. With fused kernels in every scope, ExactLoop ran at 0.40× the base engine’s throughput in synchronous eager mode at batch 1 (TPOT 118 to 296 ms, single run), and its prefill at 32 requests took 3.08 instead of 2.32 s. A Triton launch from Python costs more than the PyTorch kernels it replaces on this host. Graph-only fusion removed the regression in prefill (Table A3).

A full graph cache turns decode eager without warning. The engine captures one recurrent graph per batch size, 16 by default, and runs every later size eagerly. Staggered PD imports and sessions pass through more sizes: with 16 graphs, 3 of 23 PD runs decoded five times slower at 32 requests, and session runs fell back to eager execution hundreds of times. ExactLoop keeps 64 graphs and evicts the least recently used one once full; with 64 graphs no PD or session run fell back. Both changes decide which steps replay a graph, not what they compute (r0).

The KV path chose TCP, and TCP was not the bottleneck. NIXL’s UCX plugin requests peer failure handling, which shared-memory and CUDA IPC transports lack, so UCX fell back to TCP. Removing that requirement moved the KV to CUDA IPC but barely shortened a chunk; the commit tail was set by budget rounds times the engine step, which the larger in-flight budget removes (details in the appendix).

7 Related Work

LLM serving. Paged KV caching Kwon et al. (2023), iteration-level scheduling Yu et al. (2022), prefix sharing Zheng et al. (2024), and chunked prefill Agrawal et al. (2024) underpin most serving engines. PD disaggregation Zhong et al. (2024); Patel et al. (2024) and KV-centric designs Qin et al. (2025) move KV between machines; they assume one KV entry per layer, which looped models multiply by depth.

Variable depth and numerics. Weight sharing across depth goes back to Universal Transformers Dehghani et al. (2019); Huginn Geiping et al. (2025) and Ouro Zhu et al. (2025) use it, while CALM Schuster et al. (2022) and LayerSkip Elhoushi et al. (2024) also vary compute per token. Speculative decoding Leviathan et al. (2023); Chen et al. (2023) and self-speculation Zhang et al. (2024) help only while the target model leaves the GPU idle. Batch-size-dependent kernels make outputs depend on server load He (2025); double rounding and contraction are classical Higham (2002).

Looped-model inference. Continuous depth batching Schwethelm et al. (2026) schedules single loop iterations so that rows at different depths share a batch; the base engine we measure implements its runtime ideas, and ExactLoop builds on it rather than replacing it. WaveFront Ha & Kim (2026), LoopSpec Cho et al. (2026) and LoopAhead Liu et al. (2026) draft tokens from shallow recurrent states and verify them at full depth; FlashLoop Yang & Liu (2026) skips cross-loop updates and quantizes KV residuals, and ResidualQuant Kim et al. (2026) stores non-final loops’ KV as 2-bit residuals. They report speedups over autoregressive decoding or full-precision KV, not over a tuned engine, and change what is computed: speculation preserves the output distribution by verification, while sparsity and quantization approximate it. ExactLoop’s r0 and r1 changes alter at most which rows share a batch, need no accuracy check, and are orthogonal to these methods; we have not measured them in combination.

Looped models in RL. A concurrent submission Anonymous (2026) checks learner log-probabilities against deferred-loop rollouts on the same engine; we study serving.

8 Conclusion

Looped models repeat per-layer costs at every depth. Huginn wastes KV on dead depth layers; Ouro launches many small kernels. Live-slot packing and fenced fusion remove both without changing same-batch arithmetic. Packed prefill, position-keyed noise, graph management, and a polling-aware transfer budget supply the remaining gains. Under Poisson arrivals of real prompts, ExactLoop moves Ouro’s saturation to a higher rate but not its saturated throughput, and Huginn’s ExactLoop arm had not saturated.

Appendix B Additional Limitations

The real-prompt replay ran on the standalone host only, with one round per arm and the last of two runs per rate; it shares the release table’s platform but not its workloads. Prompt and answer lengths were capped at 1024 and 256 tokens, which keeps 911 of 2000 ShareGPT requests. 2 of 10 Poisson runs of Ouro’s unmodified released defaults aborted with an illegal memory access, both at 4 requests/s and neither in the same place of an exact replay. A GPU core dump of the second abort shows a Warp MMU fault in a cuBLAS split-K GEMM (nvjet, sm_90) right after a tensor-memory-accelerator store, that is, a GEMM output or workspace address that was no longer mapped; ExactLoop’s Triton kernels were not running. One run each with packed prefill, fused kernels or asynchronous scheduling disabled did not abort, which at this rate is not evidence. We suspect a tensor freed on one stream while another still used it, but the cause remains open. Our pre-registered online criterion, the highest rate whose median latency per token stays within twice the engine’s own lowest-rate value, rated ExactLoop and the base engine equal for both models, so the predicted 1.5-fold gain in sustainable rate was not met; the criterion takes ExactLoop’s lower floor as its reference, and an absolute threshold would have been the better choice. Ouro-2.6B was measured for throughput and token identity only, not accuracy.

The released-defaults comparison, packing and kernel component tables, and final PD comparison retain two of three runs per cell; earlier characterization and component tables often have one. At 32 requests, variation on the standalone host overlapped several component differences, which we report as ties. Huginn’s prefill share was measured only at 32 and 64 requests and in one session run. Ouro sessions on the paper tree come from the batch-scheduled host; the release table and the Huginn sessions come from the standalone host, where the Ouro release gains are smaller (ledger rows 48 and 52).

Huginn’s GPU prefix-reuse check used 128 prompts, eight for the sequential generator. The first Ouro accuracy checks use 87 questions; the noise, cache, packed-prefill and repeated kernel checks use the full 1319-question split. For packed prefill the 95% intervals still reach −1.5 (Huginn) and −2.1 points (Ouro). Bitwise kernel results apply to the tested shapes, PyTorch/CUDA versions, and GPUs. A capacity change can still alter GEMM batch shapes and therefore the generated tokens.

PD experiments used one node because the engine starts workers locally; a cross-node path would have used TCP on our systems. The fastest IPC result disables UCX peer error handling, leaving failures to the control channel. Session traces contain long, repetitive prompts and may overstate cache hits elsewhere. We evaluate Ouro at depth four and Huginn at depth 32 with fixed decoding depth. We have not measured adaptive exits, other recurrence depths, larger models, or other GPU families.

The evaluation has no non-looped baseline of matched quality. It therefore shows how much of the looped-model overhead the engine removes, not whether a looped model is cheaper to serve than a standard model of the same quality. Both looped models are small, the upstream engine release is labeled experimental, and all GPU results come from one GH200 host type and one RTX 5090. Huginn packed prefill is within the one-point rule on its point estimate only (see the accuracy checks in the main text).

Appendix C The KV Path: TCP Was Not the Bottleneck

NIXL’s UCX plugin requests peer failure handling by default. Shared-memory and CUDA IPC transports have no peer failure handler, so UCX falls back to TCP for active messages and emulates remote writes with them; removing TCP from the allowed transports made the PD engines fail at startup. With the backend created with error handling disabled, UCX’s log showed CUDA IPC and shared memory and no TCP lane, and the engines also ran with TCP removed. A 64 MB chunk still took 16.9 instead of 20.0 ms, the commit tail stayed near one second, and behind per-row prefill a chunk still took 51.7 ms. Chunks are submitted, and their completion is observed, only between engine steps, under a fixed in-flight budget, so the tail is set by the number of budget rounds times the step length. That is why the larger budget helped and the faster link did not. A budget that holds one request’s KV, 256 MB chunks and 2 GB in flight for 1.6 GB per request, removes the rounds: in two runs each the commit tail fell from 0.96–1.05 s to 17 ms, the median TTFT from 3.38–3.91 to 2.01 s, and throughput rose to 463.4–466.0 tokens/s. A 1 GB budget, two rounds, kept most of the tail. Holding one request’s KV is a property of this load, not a rule: with 8192-token prompts at 8 requests, where one request’s KV exceeds 2 GB, the tail was 41 ms with 2 GB in flight, 43 ms with 8 GB and 0.08–0.27 s with 256 MB (the PD table of the main paper), so what counts is the KV still in flight when prefill compute ends, against the budget. ExactLoop’s default budget is now 2 GB; in-flight bytes are not a buffer, since NIXL writes straight from the prefill pool into the decode pool. Disabling error handling has a cost: peer failures then surface only through the control channel.
