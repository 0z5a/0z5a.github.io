1 Introduction

Ternary language models restrict their weights to {−1,0,+1} and store them in about two bits each Ma et al. (2024). An eight-billion-parameter model then reads about 2 GB per generated token, which brings single-stream decoding within reach of CPU servers, whose memory bandwidth, spread over several sockets and sub-NUMA nodes, adds up to hundreds of GB/s. On one NUMA node, decoding is close to bandwidth-bound: each token reads all weights once, and the best runtimes use 72–78 % of the node’s bandwidth.

Using the whole machine is harder. Across the four NUMA nodes of a dual-socket Ice Lake server, the fastest ternary runtime we found, ik_llama.cpp (ik), reads DRAM at only 48 % of the machine’s local read bandwidth (Llama3-8B); on an Emerald Rapids server it becomes 3–12 % slower when given 104 instead of 64 cores. The natural diagnosis is weight placement, and placing every weight row on the node of the thread that reads it is indeed necessary; recent systems such as ArcLight Xu et al. (2026) build on node-local tensor parallelism.

This paper asks what limits decoding after weight placement is solved. We fix placement inside ik and then replace its execution model by an engine that keeps ik’s kernels and weights but synchronizes only a few times per layer, on two generations of Xeon servers, with three ternary models and the same models in three non-ternary formats. Time moves from reading weights to waiting at synchronization points (Fig. 1). This shift has been observed for weights that fit in GB-scale caches Zhang et al. (2026) and for fast GPU memory Chen (2026); we show that it already limits DRAM-bound decoding on standard multi-node servers, decompose the waiting, and compare dataflows to find which of their properties reduces it. Our contributions are:

  • Characterization (§4). Fixing placement and the obvious synchronization costs inside ik gains 1.20–1.73×, and further changes within its operator-at-a-time execution gain nothing. With node-local weights and two global barriers per layer, threads still wait for 20–48 % of each token, mostly for the last thread of their own node; on Emerald Rapids, the share grows with the number of threads per barrier and with fewer bytes per token.
  • Dataflow comparison (§5). On identical kernels, a row-owned dataflow without cross-node reductions loses to the Megatron-style column split in all 24 configurations, by 5–46 %. The number of global barriers (5 vs. 2 per layer) explains a minority of the gap; the traces attribute most of it to late threads and the leaders’ serial work, and a controlled variant clears the row-owned dataflow’s cross-node writes.
  • Evaluation (§6). Where decoding is DRAM-bound, the engine decodes 1.53–2.05× faster than ik with all cores and, with Q4_0, 1.39–2.25× faster than ArcLight, at ik’s accuracy and with less energy per token. It keeps this advantage at a context depth of 8192, also against ik with its KV cache interleaved over the nodes (by default ik puts the whole cache on one node).

2 Background and Motivation

Ternary LLMs on CPUs. Ternary models such as BitNet b1.58 Ma et al. (2024) restrict every weight of the linear layers to {−1,0,+1} times a per-tensor or per-row scale and quantize activations to int8. CPU runtimes for them include llama.cpp ggml-org (2026) (TQ1_0, TQ2_0), bitnet.cpp Wang et al. (2025), the table-lookup kernels of T-MAC Wei et al. (2025) and Vec-LUT Li et al. (2026b), and ik ikawrakow (2026), a fork of llama.cpp with its own ternary formats IQ1_BN and IQ2_BN. In our measurements, the 2-bit formats of these runtimes decode at about the same speed on one node, and ik is the fastest once several nodes are used; it is our baseline. Decoding multiplies the activation vector with every weight matrix, so each token reads all weights once: on one Ice Lake node with 16 threads, the DRAM reads per token of Llama3-8B are 1.01–1.04 times the weight bytes in every format we measured, and the 2-bit formats reach 72–78 % of the node’s read bandwidth, so going faster requires more nodes.

Multi-node servers. A dual-socket server with sub-NUMA clustering exposes each socket as two NUMA nodes with their own memory controllers (Table 1). Reading another node’s memory costs little within a socket on Ice Lake but 38 % across sockets, and 22–23 % for any remote node on Emerald Rapids; interleaving memory over the four nodes yields only 48–55 % of the bandwidth available when every thread reads its own node. Using the whole machine therefore requires that each thread reads weights placed on its own node.

Existing runtimes stop at half the bandwidth. The llama.cpp family offers two ways to use several nodes: interleaving the weights, and --numa distribute, which binds threads to nodes and lets the first touch of the memory-mapped weights place each page near its first reader. On Ice Lake with Llama3-8B, interleaving reaches 2.08× the single-node speed and distribute 2.44× (174 GB/s), only 49 % of the machine’s local bandwidth (48 % by DRAM counters in our main batch, §6.2); with all weights on one node, 64 threads are no faster than 16. On Emerald Rapids, ik with 104 threads decodes 3–12 % slower than with 64 threads on all three models, and a user of llama.cpp has reported a tenfold drop in decode throughput between 16 and 17 threads on another Emerald Rapids machine kimddong0069 (2026). Two properties of ggml, the tensor library under llama.cpp and ik, suggest why. It executes the model graph one operator at a time, each a parallel region that ends in a global barrier, about 17 times per layer; and operators on a single row (RMS norm, residual add, activation quantization) run on one thread while all others wait, after which threads on all nodes read the result. Section 4 measures what these costs amount to once the weights are placed correctly.

3 Methodology

Platforms. We use two dual-socket Intel servers of consecutive generations with four NUMA nodes each (Table 1); the Emerald Rapids machine has 5.4× the L3 capacity of the Ice Lake machine. Both run Linux 6.8 and are shared with other users; frequency scaling is left at its default (we record decode-phase frequencies instead, §4.4), and Emerald Rapids runs automatic NUMA balancing.

Models. We use three ternary Llama-architecture models: Llama3-8B-1.58-100B-tokens (HF1BitLLM) with eight KV heads, and Falcon3-10B-Instruct-1.58bit and Falcon3-1B-Instruct-1.58bit (TII) with four. Each is converted to F16 and quantized to ik’s IQ2_BN (2 bits per ternary weight, exact) for the main experiments and with llama.cpp to Q2_K, Q4_0 and Q4_K_M for the format study (§4.3); the output projection is Q6_K in all files. With IQ2_BN, a decoded token reads 2.19 GB (Llama3-8B), 2.73 GB (Falcon3-10B) and 0.51 GB (Falcon3-1B) of weights and KV cache, computed from the GGUF headers.

Systems. ik is ik_llama.cpp at commit 0821d62 with one thread per physical core (64 on Ice Lake, 104 on Emerald Rapids), --numa distribute and memory-mapped weights, which we evict from the page cache and touch once with ik before each model so that each page lands on the node of its reader. ik-P is ik with our four patches (Table 2), each switchable at run time. Row and Col are the two dataflows of our engine (§5); it pins one thread to each physical core, links ik’s kernels and binds weights, KV cache and per-node buffers to their node with mbind, so automatic NUMA balancing moves practically none of its pages, against 105 or more of ik’s per run. Later builds only add switches that are off by default. Below four nodes, ik and ik-P run with --numa numactl and threads and memory bound to the nodes used. Since ik allocates its KV cache on one node (§6.4), for long contexts and batches we also run it with the cache interleaved (numactl --interleave=all) and compare against the faster configuration.

Protocol. We measure the rate of generating 128 tokens (tg128) after a context of a given depth (0 unless stated), with llama-bench for ik and the engine’s own timer for Row and Col (after 4 warm-up tokens), and batched decoding with llama-batched-bench. What a table or figure compares was measured together: each of 5–6 rounds runs every variant once, in rotating order, and we report median speeds and, for ratios, the median of the per-round ratios. The speed of one binary drifted by up to 10 % from day to day while these ratios did not, so we do not compare numbers across batches. Both machines were shared; a round starts only on an idle machine and is repeated if other processes used more than a few CPUs during it (Appendix A), and such load, if anything, lowers Col’s speedup over ik (its per-round value is weakly anticorrelated with the load, Spearman’s ρ from −0.12 to −0.46). Counters (frequency, UPI traffic, memory-controller reads, RAPL energy) are differences between a 640- and a 128-token run in the same round.

4 Where Does the Time Go After Placement?

4.1 Fixing placement within ik

We start from the placement ik already achieves and add the changes of ik-P one at a time (Table 2); the increments depend on this order, which adds placement first. After ik’s first pass over its memory-mapped weights, 97 % of the weight pages already sit on the node of the thread that reads them, so migrating the rest gains only 0–3 % (6–14 % on the small Falcon3-1B). The largest step on both platforms is synchronization: replacing ggml’s global barrier by a two-level one (threads meet within their node, then one thread per node meets globally) gains 10–14 % on Ice Lake and 20–44 % on Emerald Rapids. Splitting single-query attention over KV chunks helps models whose few KV heads leave most threads idle in ik’s schedule: the Falcon3 models, and on Emerald Rapids also Llama3-8B (8×256<32×104, ik’s threshold for splitting). Removing one change at a time from ik-P on Emerald Rapids gives the same order: without the two-level barrier it loses 18–35 %, without split attention 9–17 %, without migration 1–9 % and without the AVX-512 quantizer 0–2 %. Beyond this, local changes inside ggml stop paying off: spreading the single-row operators over all threads slowed the Falcon3 models by 5–9 %, and three variants of node-local activation quantization stayed within ±2 %, because the activation vector still has to be gathered from all nodes before the next operator. What remains is ggml’s execution model, one parallel region and one global barrier per operator, about 17 per layer. Replacing it by our engine (§5), with the same kernels and only a few barriers per layer, gives 1.40–2.24× (Row) and 1.53–3.23× (Col) over ik.

4.2 How much of a token is synchronization?

The engine records, per token, how long each thread waits at global and node barriers and for its node leader, which normalizes and quantizes each stage’s input alone. With node-local weights and 2 instead of about 17 global barriers per layer, threads still wait for 22–35 % of each token on Ice Lake and 20–48 % on Emerald Rapids (Fig. 2). Recording each thread’s entry and exit at every barrier for 32 tokens, which changes the speed by about 1 %, splits this wait: a thread waits for the last thread from its own entry until the last entry, and for the barrier itself from then until its exit. Waiting for the last thread is 17–26 % of the token on Ice Lake and 14–31 % on Emerald Rapids (65–86 % of the wait), barrier latency 1–6 and 3–12 %, and waiting for the node leader 2–3 and 3–5 %. More than half of the late arrivals are threads of the waiting thread’s own node, which read equal shares of node-local weights yet finish at different times; we have not identified the cause. The share grows with the number of threads per barrier: with IQ2_BN and 13, 20 and 26 cores per node of Emerald Rapids, Col’s threads wait for 18–31, 23–42 and 29–48 % of the token, mostly through late threads, while other processes kept a median of only 0.4–0.5 CPUs busy at every core count and the share does not correlate with them (Spearman’s ρ of −0.05). On Ice Lake the share rises similarly (13–20, 18–27 and 24–34 % with 8, 12 and 16 cores per node), but about two foreign CPUs were busy throughout, and once every core is in use they can only run on the sibling hyperthreads of our threads or preempt them, so this trend is partly confounded with interference. The share is largest for Falcon3-1B, which reads only 0.5 GB per token; on Emerald Rapids, where it runs largely from L3 (§6.2), nearly half of each token is spent waiting, and with 18 thin layers barrier latency alone is 9–12 %.

4.3 Fewer bytes, more synchronization

If the waiting cost a roughly fixed time per token while the streaming time grew with the bytes read, fewer bytes per token would mean a larger synchronization share and a larger gain from a better dataflow. We test this by running each model in up to four formats: the ternary IQ2_BN and the non-ternary Q2_K, Q4_0 and Q4_K_M, which read 1.3–2.1× as many bytes. On Emerald Rapids the relation holds for both models with four formats: from IQ2_BN to Q4_K_M, the share of Col falls from 34 to 22 % for Llama3-8B and from 48 to 39 % for Falcon3-1B, and the speedup over ik from 2.05 to 1.53× and from 3.12 to 2.57× (Fig. 3). On Ice Lake it is weak: the shares of Falcon3-1B stay within 30–35 %, and Llama3-8B in Q2_K has the highest share and the lowest speedup (1.20×), an exception that coincides with ik already using more bandwidth with Q2_K than with IQ2_BN there (51 vs. 46 %). Across models the ordering holds on both machines: the model with the fewest bytes per token has the largest share and the largest speedup in every format. Quantitatively, the absolute wait is not fixed: it grows with the work between barriers (for Col with Llama3-8B on Ice Lake from 1.9 ms per token with IQ2_BN to 3.2–3.4 ms with Q4), because so does the load imbalance a barrier absorbs.

4.4 Ruling out frequency and placement

Could the engine simply place data better than ik in ways the ladder misses? Decode-phase core frequencies agree within 8 % (Emerald Rapids: 2.89 GHz for all; Ice Lake: 2.98–3.25 GHz for ik, 2.93–3.02 for Col), so the speedup is not from frequency. Cross-socket traffic (UPI data flits per token) is 4.1–7.3× higher for ik than for Col on Emerald Rapids and 5.6–7.1× on Ice Lake although both read the same weight bytes; it comes from each layer’s activation exchange and synchronization. The share of demand loads served by remote DRAM (33–58 % for ik on Ice Lake, 1–2 % for Col) misleads, as the streamed weights arrive almost entirely through the prefetcher (L3-miss stall cycles are 0.5–10 %).

5 Row-Owned vs. Column-Split Dataflow

To find which property of a dataflow matters, we built a decode engine that keeps ik’s kernels and GGUF weights and runs two dataflows that differ in how often all threads meet and how much data crosses nodes.

5.1 The engine

The engine is one process with one thread pinned to each physical core. At load time each weight matrix is cut into one slice per node and one range of rows per thread, and each slice is copied into memory of its node. Threads compute their rows with ik’s matrix–vector kernels and quantize activations with ik’s quantizers, so both dataflows perform ik’s arithmetic on the same weights. Before each matrix stage, one leader thread per node normalizes and quantizes the stage’s input into a node-local buffer. Element-wise operations (RoPE, SiLU, residual add, writing the f16 KV cache) are done by each thread on the rows it just computed, without extra barriers; barriers are two-level, as in ik-P.

5.2 Two dataflows

Row-owned (Row). Every matrix is split by output rows across all threads of all nodes. Since the next stage’s node leaders need whole vectors, each thread writes its output rows into a copy of the vector on every node, a parallel scatter instead of a serial gather. A layer has five stages (QKV, attention, O with residual, gate/up with SiLU, down with residual), each ending in a global barrier, and no reductions (Fig. 4). Avoiding cross-node reductions is meant to keep the traffic between nodes small; the scatter writes instead generate more cross-socket traffic, although §5.4 shows that this traffic is not what slows Row.

Column-split (Col). This is the Megatron-LM decomposition Shoeybi et al. (2019), which ArcLight Xu et al. (2026) applies to the NUMA nodes of a CPU. Node n owns a quarter of the query heads with their KV heads and KV cache, and a quarter of the FFN’s intermediate dimension, and computes them with node-level barriers only. O and down are split by input columns, so each node obtains a partial sum of the whole hidden vector; after a global barrier, every node adds the four partial sums into its residual copy in a fixed order, so the copies stay identical. A layer has two global and six node barriers, at the price of two reductions in which each node reads three remote vectors of the hidden size (16 KiB for Llama3-8B).

5.3 Comparison

Col is faster than Row in all 24 configurations of Table 3, by 5–21 % on Ice Lake and 11–46 % on Emerald Rapids. The gain is largest for Falcon3-1B, larger with IQ2_BN than with the 1.7–2.1× larger Q4_0 in 11 of 12 cases, about twice as large on Emerald Rapids, and persists at depth 4096, in line with the wait shares of Section 4.

Two stages shrink (Fig. 5). The barrier wait falls by 7–23 % on Ice Lake and 25–35 % on Emerald Rapids. The QKV stage, whose time excludes the barrier wait, becomes 36–57 % shorter: in Row, K and V rows go to the node that holds the KV block of the token’s position and Q to a shared buffer, so most threads write across nodes, whereas in Col a node’s heads, Q and KV cache stay on the node. The reductions add at most 0.22 ms per token to O and down, while the token time drops by 0.38–1.45 ms: the partial sums never travel as messages, each node reads them from shared memory after the barrier. Col also gives the node leaders less serial work: the inputs of O and down are the node’s own slices of the attention output and the FFN activation, so a leader quantizes 39–48 % as many elements per layer as in Row, and on Emerald Rapids the slowest leader’s time per token falls by 37–52 %.

5.4 Isolating the number of barriers

The two dataflows differ both in the number of global barriers and in where they read and write, so we separate the two in the engine (Table 4). Promoting three of Col’s node barriers to global ones gives it the five global barriers per layer of Row with its own data placement, and adding empty global barriers right after an existing one, when all threads have just met, measures barrier latency without imbalance; neither changes the computed values.

The number of barriers explains only a minority of the gap: five global barriers per layer slow Col by 5–26 % of the Row–Col difference, and three complete extra barriers by 16–38 %. An empty global barrier among 104 threads costs 1.4–4.4 μs, so Col’s two per layer take 1–10 % of its token time, a small part of its 20–48 % wait. On Ice Lake the round-to-round variation of the shared machine (4–11 %) exceeded these effects (Appendix E).

Row also writes across nodes (each thread writes its output rows into every node’s copy and its K and V rows to the node holding the token’s KV block), with 4.1–5.0× the cross-socket traffic of Col on Emerald Rapids and 1.8–2.4× on Ice Lake; its leaders quantize more than twice as many elements; and it splits attention by position rather than by head. In the traced batches (not that of Table 4), the gap of 0.43–2.67 ms per token consists of Row’s longer waits for late threads (up to 1.29 ms) and for the leaders (up to 0.54 ms) and its longer QKV, attention and gate/up stages (up to 0.62, 0.15 and 0.19 ms), less Col’s reductions (up to 0.23 ms); barrier latency adds at most 0.08 ms, and the residual is below 0.14 ms (Appendix F). The cross-node writes of the stage outputs do not explain the extra waiting: a variant of Row that writes the outputs of O, gate/up and down only to its own node and copies the other nodes’ rows after the barrier (bit-identical results) is 1–7 % slower and waits as long for late threads (−4 to +3 %). Row’s extra late arrivals occur mainly at the barriers after QKV and attention, which also differ in the K and V writes and the attention split.

5.5 Comparison with ArcLight

ArcLight implements the same decomposition on top of llama.cpp’s operators and kernels and supports only F16, Q4_0, Q8_0 and Q6_K weights, so we compare with Q4_0, the format it was evaluated with Xu et al. (2026) (Table 5). ArcLight runs at 0.72–1.00× the speed of ik, and Col is 1.39–2.25× (Ice Lake) and 1.74–3.23× (Emerald Rapids) faster than ArcLight (llama.cpp is unusually slow on Ice Lake because it repacks Q4_0 weights into a buffer on one node). On one node of Emerald Rapids, ArcLight is within 4–11 % of ik and Col only 1.05–1.23× faster, whereas on four nodes Col is 1.81–3.59× faster in the same batch, so the gap arises across nodes. The decomposition alone therefore does not deliver the speedup; across nodes, ArcLight executes llama.cpp’s operator graph with node-level barriers inside its tensor-parallel subgraphs and global ones at their boundaries Xu et al. (2026), whereas Col runs each stage as one parallel region.

6 Evaluation

6.1 Decode throughput

At depth 0, Col decodes 1.53, 1.65 and 2.00× as fast as ik on Ice Lake and 2.03, 2.05 and 3.23× on Emerald Rapids for Llama3-8B, Falcon3-10B and Falcon3-1B (Table 2), with 95 % bootstrap intervals within 4 % of the medians; on another Ice Lake machine and other days, the ratios of the engine changed by less than 5 %. ik is not always fastest with all cores: on Emerald Rapids it is 6–14 % faster with 64 or 80 of its 104 cores, and on Ice Lake Falcon3-10B is 6 % faster with 32 of 64. Against ik at its fastest thread count, Col is 1.53, 1.54 and 1.93× faster on Ice Lake and 1.89, 1.92 and 2.78× on Emerald Rapids. Among existing runtimes ik is the fastest on both machines: on Emerald Rapids, llama.cpp (TQ2_0, Q4_0) and bitnet.cpp (I2_S) reach 0.59–0.85× of its speed, and the two weight-replication pull requests matteoscalabrini (2026); SamuelOliveirads (2026) do not improve on it (Appendix D).

6.2 Bandwidth utilization

Decode speed times bytes per token gives a kernel-independent effective bandwidth (Fig. 6). Col reaches 63–71 % of the machine’s local read bandwidth on Ice Lake and 70–78 % on Emerald Rapids, against 31–46 % and 24–37 % for ik. Memory-controller counters confirm this on Ice Lake, whose 48 MiB L3 per socket holds little: DRAM reads per token are 92–103 % of the weight and KV bytes, and Col uses 59–71 % of the bandwidth against 32–48 % for ik. On Emerald Rapids, 9–20 % of the bytes of the two larger models come from the 260 MiB L3 per socket, so by measured DRAM reads Col uses 60–61 % and ik 28–31 %. Falcon3-1B (482 MiB of weights) runs on Emerald Rapids almost entirely from L3, with only 0.03–0.06 of its 0.53 GB per token from DRAM; its 3.2× speedup there measures on-chip synchronization and computation, consistent with its 39–48 % barrier share (Fig. 2). On Ice Lake, this is close to what every implementation reaches on a single node (§6.3), so the remaining limit there is the kernel.

6.3 Scaling over nodes

On one node the implementations differ by at most 17 % and all reach 70–84 % of the node’s bandwidth (Fig. 7). From one node to four, ik speeds up only 1.77–2.36× (Ice Lake) and 1.29–1.82× (Emerald Rapids), while Col speeds up 3.0–3.3× and 3.4–3.7× (on Emerald Rapids partly helped by the larger L3 of more nodes). The engine’s advantage therefore arises across nodes.

6.4 Context depth and KV-cache placement

Long contexts exposed a placement issue in the baseline: ik allocates the whole KV cache on a single node. Interleaving it with numactl --interleave=all, which needs no code change, makes ik faster at depth 8192 by 19, 38 and 60 % on Ice Lake and by 36, −3 and 76 % on Emerald Rapids (Llama3-8B, Falcon3-10B, Falcon3-1B), but slower at depth 128 by 15–20 % on Ice Lake and 11–13 % on Emerald Rapids for the larger models (Appendix I). On Emerald Rapids, automatic NUMA balancing moves a varying part of the cache during each run (the most loaded node held 27–55 % of it), so the default placement there is also unstable (Appendix G). Against the faster of the two ik configurations at each depth (Fig. 8), Col is 1.46, 1.59 and 1.86× faster on Ice Lake at depth 128 and 1.66, 2.08 and 2.49× at 8192, and on Emerald Rapids 2.00, 2.02 and 3.23× at 128 and 2.02, 2.44 and 2.93× at 8192: its advantage holds at every depth, growing by 13–34 % on Ice Lake but not on Emerald Rapids. Against ik’s default placement alone, the depth-8192 ratios would have been overstated as 1.97–3.94× and 2.44–5.17×. With the interleaved cache, ik-P is 1.17–1.33× (Ice Lake) and 1.24–1.71× (Emerald Rapids) faster than the faster ik at every depth.

6.5 Batches, prefill, energy and accuracy

Batches. The engine decodes a single sequence; with llama-batched-bench, ik-P’s gain over ik is 1.21–1.31× (Ice Lake) and 1.38–1.59× (Emerald Rapids) at one sequence but only 1.02–1.17× at eight or more, while batching itself raises ik’s throughput 1.9–3.4× (Appendix H). Col therefore targets the latency of a single sequence, as in interactive decoding.

Prefill. The engine does not process prompts; prefill is a compute-bound matrix product, which we accelerate separately inside ik with AMX tiles (Appendix J). This is 1.43–2.07× faster than ik’s fastest prefill on one node of Emerald Rapids but only 1.08–1.39× on the whole machine, where ik’s per-operator synchronization again limits scaling.

Energy. Measured with RAPL over the whole machine (package and DRAM), Col uses 29–45 % less energy per token than ik on Ice Lake and 39–64 % less on Emerald Rapids (Appendix C). On Ice Lake all implementations run at the package power limit, so the saving follows the speedup; on Emerald Rapids Col draws 16–29 % more package power than ik, so the saving is smaller than the speedup. RAPL covers the whole machine, so the readings include other users’ processes; the difference between two run lengths removes only their constant part.

Accuracy. All paths quantize activations to int8 and differ slightly from an F16 reference with the same ternary weights; on 5100 WikiText-2 tokens, ik’s two decode paths (with and without flash attention) have perplexities within 0.4 % of the reference and KL divergences of 0.0030–0.0045. Row falls within this spread, and Col, which quantizes the inputs of O and down per node and thus with finer scales, has the lowest KL divergence of all paths (0.0020–0.0034). Over 256 greedy tokens, Col reproduces ik’s output for 7–11 of 32 prompts, as often as ik’s two decode paths agree with each other (6–8); Appendix B gives the details.

7 Discussion and Limitations

Generality. The effect is not specific to ternary weights: with Q4_0 and Q4_K_M, Col is still 1.40–2.57× faster than ik and threads wait for 20–39 % of a token (Figs. 2, 3); formats with even fewer bytes, such as BITCOS at 2−z bits per weight for a zero fraction z Georganas et al. (2026), should make the dataflow matter more.

Implications for CPU runtimes. First, on multi-node machines one global barrier per operator, with single-row operators on one thread, costs more than misplaced weights; grouping a layer into a few stages is the larger lever, and beyond that, how the work is divided among threads matters more than the barrier count. Second, most of the remaining wait is imbalance among a node’s threads, which fixed row ranges cannot absorb; assigning rows dynamically within a node is the direct remedy to test. Spreading the leader’s serial work (3–5 % of the token) over the node’s threads made Col 3–22 % slower, because the threads must then exchange statistics and meet once more per stage; letting every thread quantize the whole vector itself would avoid both. Third, the KV cache should be placed like the weights: an interleave makes ik up to 76 % faster at depth 8192 than its single-node default. Fourth, thresholds tuned for one machine break on another: ik’s rule for splitting single-query attention leaves most threads idle at short context for models with four KV heads and, at 104 threads, also for Llama3-8B.

Scope. Col supports Llama-architecture models whose head, KV-head and FFN counts are divisible by the number of nodes and whose head size is a multiple of 128, and decodes a single sequence without prefill or batching; it targets latency-bound single-user settings (§6.5). Of the public ternary models, Llama3-8B-1.58 is fine-tuned from a full-precision model, and BitNet b1.58 2B4T, trained ternary, uses squared ReLU and extra sub-layer normalization, which the engine does not implement. Hybrid-attention models, more than four NUMA nodes, AMD systems and Intel systems with SNC disabled are outside our measurements, and Emerald Rapids’s large L3 makes its Falcon3-1B results reflect on-chip rather than memory behavior.

Threats to validity. Sharing the machines matters little for the comparisons between implementations, whose variants alternate within every round and are hit alike by other users’ load (§3). Absolute wait shares may be affected: in the trace batches of Fig. 2 the share grows with interference (Spearman’s ρ of 0.36 on Emerald Rapids and 0.52 on Ice Lake); on Emerald Rapids, medians over rounds with at most one busy foreign CPU differ by at most 3.3 points, but Ice Lake never had fewer than 1.8 busy foreign CPUs, so its shares may be a few points high, and its thread-count trend is partly confounded with interference (§4.2).

8 Related Work

Numbers quoted here are those reported by the cited works on their platforms.

Multi-node CPU inference. ArcLight Xu et al. (2026) is the closest prior work: it groups threads by NUMA node, partitions weights in the Megatron-LM style Shoeybi et al. (2019), synchronizes globally only at the boundaries of its tensor-parallel subgraphs, and reports up to 46 % higher throughput than mainstream frameworks. Col uses the same decomposition; our contribution is the measurement of what limits decoding once it is in place and the comparison with a row-owned dataflow on identical kernels (on our machines Col is 1.39–3.23× faster than ArcLight). SGLang’s CPU backend maps tensor parallelism to NUMA nodes with shared-memory collectives and reports that communication takes 3 % of the end-to-end time overall, in deployments centered on large MoE models such as DeepSeek-R1 Intel PyTorch Team (2025), consistent with synchronization weighing less when more bytes are read. xFasterTransformer distributes inference over sockets and machines He et al. (2024), KTransformers splits MoE expert weights across sockets in a CPU/GPU hybrid Chen et al. (2025), and two pull requests replicate weights on every node matteoscalabrini (2026); SamuelOliveirads (2026).

Synchronization when data movement shrinks. On CPUs whose 3D-stacked last-level caches hold the weights, Zhang et al. (2026) find that operator-boundary synchronization becomes a visible bottleneck and relax it to sub-operator dependencies; on GPUs, Chen (2026) finds that batch-1 decoding reaches a smaller fraction of peak bandwidth the faster the memory, and attributes the gap to kernel-launch overhead. We show the same shift for DRAM-bound decoding on standard multi-node servers, quantify it against the bytes per token and the threads per barrier, and compare dataflows on identical kernels; our Emerald Rapids results for Falcon3-1B fall into the cache-resident regime of Zhang et al. (2026).

Reducing synchronization on GPUs. GPU decoders fuse a forward pass into one persistent kernel with few synchronization points per layer, hand-written Spector et al. (2025a); Spector et al. (2025b), generated by agents or search Li et al. (2026a); Dong et al. (2026); Jaber & Jaber (2026), or for multi-die GPUs whose dies resemble NUMA nodes Chowdhary et al. (2026). On CPU nodes, we find that reducing the number of synchronization points stops paying off once they are few (§5.4).

Ternary and low-bit kernels; AMX. Ternary CPU work mostly optimizes the kernel on one node or socket: table lookups in T-MAC Wei et al. (2025) and Vec-LUT Li et al. (2026b), lossless kernels in bitnet.cpp Wang et al. (2025), Intel’s near-roofline 2-bit microkernels Georganas et al. (2025), the sub-two-bit BITCOS format Georganas et al. (2026), and FairyFuse’s fused AVX-512 loop on one Xeon Zuo et al. (2026). They are complementary: a faster kernel or a smaller format shortens the work between barriers and makes the dataflow matter more. AMX is used for MoE experts in KTransformers Chen et al. (2025), for sparse compressed models in SparAMX AbouElhamayed et al. (2025), and for ternary prefill in Intel’s TPP-based framework. Appendix J reports an AMX ternary prefill inside ik as a side result.

9 Conclusion

Placing every weight on the node of its reader is necessary for decoding ternary LLMs on multi-node CPU servers, but threads then still wait for 20–48 % of each token, mostly for the slowest threads of their own node. On the same kernels, a column-split dataflow decodes 1.5–2.1× faster than the fastest existing ternary runtime where decoding is DRAM-bound, mainly because its threads wait less for each other and for their node leaders. Balancing the work among a node’s threads is the next target, along with integrating such a dataflow into a runtime with batching and prefill and testing it on more nodes and on other vendors’ CPUs.

Appendix A Measurement protocol

Both machines were shared with other users. A round of a batch started only after the machine had been idle for 20 s (at most two busy CPUs). After each run we computed how many CPUs other processes had kept busy on average, as the machine’s busy time minus that of the run’s own processes, per second; a round in which this exceeded 2.5 CPUs on Ice Lake (3.5 in the later batches) or 4 on Emerald Rapids in any run was discarded and repeated after a further idle period. Four early batches had only the idle check before each round: the Ice Lake rows of the paper’s Row-versus-Col and ArcLight tables, Ice Lake batched decoding (Appendix H) and the other runtimes on Emerald Rapids (Appendix D). On Emerald Rapids, medians over the rounds with at most one busy foreign CPU differ from those over all rounds by at most 3.7 %.

Appendix B Accuracy

Greedy generation. For 32 prompts and 256 greedily generated tokens each, Col produces the same 256 tokens as ik’s decode path for 11, 8 and 7 prompts (Llama3-8B, Falcon3-10B, Falcon3-1B), with the first difference at a median position of 20, 18 and 23; Row for 9, 8 and 7 prompts (median positions 26, 30, 34). ik without flash attention agrees with ik for 7, 6 and 8 prompts, diverging at median positions 20, 14 and 24. ik-P is bit-identical to ik at this thread count. Greedy decoding flips near-ties under any change of summation order, so these numbers measure closeness to ik, not generation quality.

Downstream tasks (AMX-prefill). On Emerald Rapids, AMX-prefill (Appendix J) and ik score within 1.0 point of each other on HellaSwag (1000 questions), WinoGrande (1267), ARC-Easy (570) and ARC-Challenge (299) for all three models, within one standard error and without a consistent direction (e.g., Llama3-8B 66.6 vs. 66.5, 60.06 vs. 59.91, 67.54 vs. 67.19, 40.47 vs. 40.47).

Col. Col, which quantizes the inputs of O and down per node and thus with finer scales than one scale per row, has the lowest KL divergence from the reference of all paths (Table 6; top-token agreement 96.4, 97.3 and 96.9 %). On one node its perplexity is bit-identical to Row’s. The Row rows are the current engine configuration; an earlier version with a different attention schedule, measured on 2026-10-06, gave 0.00446, 0.00374 and 0.00298.

Appendix D Other runtimes

ArcLight. We built ArcLight at commit 558ef06 (May 2026) twice, as shipped for AVX2 and with -march=native, and ran its generator with --numa tp over all four nodes, one thread per physical core (64 or 104), arenas of 12 GB for weights, 4 GB for activations, 2 GB for the KV cache and 2 GB of work space, a short prompt and 128 generated tokens; we report the decode speed it prints. Appendix E Barrier isolation on Ice Lake

We repeated the barrier isolation of the main text on Ice Lake while other users’ jobs were running there. Other processes kept 1.7–3.3 CPUs busy during the runs (we raised the interference limit to 3.5 CPUs for this batch), and since Col uses every physical core of Ice Lake, they share cores with it: Col’s token time varied by 4–11 % between rounds, more than the effects being measured (Table 9). Row is slower than Col in every configuration, and for Falcon3-1B, where the rounds agree best, three promoted barriers change Col’s token time by −0.01 ms against a gap of 0.36 ms and three empty ones add 0.06 ms, so there the barrier count explains a small part of the gap, as on Emerald Rapids. For the two larger models the intervals of both variants include zero; these runs do not resolve them.

Appendix F Accounting of the Row–Col gap

Within one batch, the measured parts account for the gap to within 0.14 ms (Table 10). Two approximations enter: the stage times are means over the whole run, and the wait is divided into its three parts in the proportions measured on the traced runs of the same batch, which cover 32 tokens. These batches are not the one of the barrier-isolation table in the main text, so their gaps differ from it (e.g., 0.83 instead of 1.01 ms for Llama3-8B with IQ2_BN on Emerald Rapids). The largest compute difference is the QKV stage, where Row writes K and V to the node that holds the token’s KV block and Q to a shared buffer; the attention stage, which Row splits by position and Col by head, differs by up to 0.15 ms. We did not isolate these two differences. Col’s reductions make its O and down stages up to 0.23 ms longer, and barrier latency contributes at most 0.08 ms.

Appendix G KV-cache placement

ik allocates the KV cache in one buffer on one node (--localalloc keeps it there). On Emerald Rapids, automatic NUMA balancing migrates part of it during each run (140–490 thousand pages per run), so the default placement varies from run to run; Ice Lake has balancing off, so there the default is the single-node case. With the cache interleaved, both ik and ik-P are stable, and ik-P is 1.27–1.28× faster than ik.

Appendix H Batched decoding

On Emerald Rapids, ik’s default KV placement collapses beyond B=8 (Llama3-8B 179.8 tok/s at B=8, Falcon3-10B 102.5 at B=16, Falcon3-1B 783.7 at B=8); interleaving the cache recovers 18–54 %. Even interleaved, throughput drops from B=8 to B=16 by 9–17 %.

Appendix I Open observations

  • Interleaving the KV cache slows ik at short context (depth 128) by 15–20 % on Ice Lake and 11–13 % on Emerald Rapids.
  • On Ice Lake, Llama3-8B in Q2_K benefits less from Col (1.20×) than in Q4_0 (1.43×), which does not hold on Emerald Rapids.
  • On Ice Lake, Falcon3-1B has a slightly higher barrier share with Col (36 %) than with Row (33 %), although Col is 17 % faster.
  • ik’s batched throughput on Emerald Rapids drops from B=8 to B=16 even with an interleaved KV cache.
  • llama.cpp’s weight-replication pull request is 22–59 % slower than llama.cpp’s own distribute mode with Q4_0 weights (Table 8).

Appendix J AMX prefill and one request

Before the first token, the prompt is processed in one compute-bound matrix–matrix pass. Emerald Rapids provides AMX tile instructions with an int8 peak of 552 Tops, 7.6 times its VNNI peak, which llama.cpp, ik and bitnet.cpp do not use for ternary weights. We add an AMX path to ik’s prefill (AMX-prefill).

Ternary GEMM on AMX. AMX-prefill replaces ik’s IQ2_BN matrix multiplication whenever at least 32 activation rows are multiplied. Each thread expands its 2-bit weight rows into the int8 layout of AMX tiles (a 32-bit gather per four input positions of 16 rows, then shift, mask and subtract), unpacks up to 1 MB of weight panels into L2, and runs all 32-token activation blocks over them; on a socket or more, work is split over both weight rows and tokens. Activations are quantized exactly as for ik’s VNNI kernel (four scales per row by channel group), with both operands reordered by group so that each 64-wide AMX step stays in one group, so AMX-prefill computes ik’s integer sums. Its perplexity on Llama3-8B is 0.9994±0.0014 of ik’s (KL divergence 0.0022), and its downstream accuracy matches ik’s (Appendix B). In a microbenchmark with Llama3-8B shapes, the kernel is 4.3–7.2× faster than the same tiling with VNNI and reaches 50 Tops on one node and 89 on one socket.

Prefill throughput. Against ik’s fastest prefill path, AMX-prefill is 1.43–2.07× faster on one node, 1.33–1.79× on one socket and 1.08–1.39× on the whole machine (Table 13). The gain shrinks with scale (from one node to the machine, ik’s prefill grows 2.6× on Llama3-8B and AMX-prefill’s 1.7×): once the matrix products run on AMX, the remaining operators and ggml’s per-operator synchronization take a larger share; we did not apply the engine’s dataflow to prefill. llama.cpp’s Q4_0 path, which uses AMX after repacking, reaches 0.69–0.78× of ik’s fastest prefill on one node or socket (2.4–3.0× its own speed without AMX); llama.cpp TQ2_0 and bitnet.cpp I2_S reach 0.36–0.56×. Intel’s TPP 2-bit GEMM, which also uses AMX, ran the prefill of Ternary-Bonsai-8B about 1.8× (one node) and 1.1× (one socket) faster than ik on the same model but decoded at 0.31–0.37× of ik’s speed; this comparison uses a different model and framework and was not interleaved. In batched decoding with 32 or 64 sequences, where decoding becomes a matrix product, AMX-prefill is 5–21 % faster than ik on one node and within noise on the whole machine.

One request. For a request with a 512-token prompt and 128 generated tokens on the whole Emerald Rapids machine (Fig. 9), AMX-prefill shortens the time to first token to 1/2.2–1/2.4 of ik’s. In one end-to-end run, ik-P with AMX-prefill completes the request 1.49–1.99× faster than ik. Adding Col’s separately measured decode time to the prefill time of AMX-prefill gives 2.01–3.07×; this is an estimate from two phases timed by different tools, as the engine has no prefill of its own. Decoding still takes 50–66 % of the request with Col.
